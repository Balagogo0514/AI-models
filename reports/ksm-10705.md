# KSM 簡報大綱（9 頁）— WLAN 大量規則異動效能調查

報告對象：AE / PM / SVD / CSO / RD
資料來源：`docs/multi-rules-add-del-config_route.md`（YAMS / zyxel-yams wlan-setting）

---

## 第 1 頁

**Title：問題動機**

### 副標
wlan-setting 大量規則異動（ADD／DELETE）效能瓶頸定位、修復與實測結果

### 動機（偵測到的問題）
- 觀察到的現象：**一次性新增或刪除大量規則時，設定套用會變得非常久** —— 日常小量修改（1～5 條）反應正常，但一次新增/刪除數百條規則時，客戶端明顯感受到系統長時間無回應
- 為了找出耗時發生在哪，埋設量測點追蹤「從 sysrepo datastore commit 完成，到對應的 `config_route()`（如 `apply_ap_group`）真正被呼叫」這段時間 —— 這段時間理論上應與規則本身的處理邏輯無關，只是框架派送開銷
- 實測證實：以一次刪除 520 個 single-ap 的實機案例為例，commit 完成後**花了近 71 秒**才真正進入 `apply_ap_group`，且耗時不隨異動規模線性成長（規模放大、耗時不成比例暴增）
- 換言之：業務邏輯本身沒有變慢，是「找到該呼叫哪個 config_route()」這一步異常地慢 —— 觸發本次針對 YAMS 框架規則派送機制（`get_changes` / `update_current_config` / `routes_from_changes`）的深入調查
- 這類「一次性大量規則異動」在大型場域布建、批次退場、設定回滾等場景下並非罕見操作，需要查清楚根因並確認是否可修復

### 結論
瓶頸主戰場 `routes_from_changes()` 已修復並上線驗證，單項提速 **11–18 倍**，端到端最慢交易從 **78 秒降到 17 秒**（約 4.6 倍）；同時發現一個尚未解決的 **~100 倍連鎖放大**現象，潛在效益比本次修復更大。

## 第 2 頁

**Title：共同問題**

### 為何不只是 wlan-setting 的問題
瓶頸點 `routes_from_changes()` 是 **YAMS 框架層**共用邏輯，不是 wlan-setting 專屬程式碼 —— 任何 YANG module 只要其 list 型態的 entries 數量夠多，一次性大量新增或刪除都會落入同一條派送路徑。

### 期待解決範圍
本次修復預期不只解決 wlan-setting，而是**任何 module 的 list 只要 entries 夠多、遇到一次性大量 ADD/DELETE，效率都能同步受益**，不需個別 module 各自優化。

### 判斷依據
- `routes_from_changes()` 掃描的對象是「全系統已註冊的 config route」，與哪個 module 觸發變更無關
- 瓶頸成因（每個 change 都要對全部 route 做 regex）是通用機制，不含 wlan-setting 專屬邏輯
- 因此凡是符合「同一次 commit 產生大量 change」條件的 module，皆屬於本次修復的受益範圍

## 第 3 頁

**Title：耗時拆解**

### 對應動機
第 1 頁量測到的「commit 完成 → `config_route()` 被呼叫」這段 ~71 秒派送時間，實際上是由三個框架層 API 依序組成，與 `config_route()` 業務邏輯本身無關：

`get_changes()` → `update_current_config()` → `routes_from_changes()` → **`config_route()` 被呼叫（ENTER）**

### 修復前各階段實測耗時（大交易 51,779 筆）
- get_changes：3.36s
- update_current_config：3.21s
- **routes_from_changes：64.30s（★ 佔派送總時間 ~91%）**
- 派送總計（commit → config_route() ENTER）：**~70.9s**
- 對照：`config_route()`（apply_ap_group）業務邏輯本身執行僅 **~4s**

### 重點
驗證了動機提出的問題 —— 慢的不是規則本身的處理邏輯，而是框架「找到該呼叫哪個 config_route()」這一步；三個候選中唯一佔比壓倒性、且本次唯一動手修改的環節是 `routes_from_changes()`

## 第 4 頁

**Title：根因分析**

### 三個瓶頸候選
（N = 這次異動產生的 change 數量；M = 全系統 config route 數，約 50 個，涵蓋 vrf／bgp／nat／wlan 等全部 service，不只 wlan-setting；P = 每個 route 的 xpath pattern 數，通常 1～2 個。三者相乘就是 `routes_from_changes()` 要做的 regex 比對總次數）

| API | 做什麼 | 複雜度 | 量級直覺（白話） | 狀態 |
|---|---|---|---|---|
| `get_changes()` | sysrepo diff 轉 Change 物件，粒度由 sysrepo 決定（YAMS 無法改變） | O(N) | change 變多，耗時等比例增加，不會突然暴增 | 已量測，非首要 |
| `routes_from_changes()` | 每個 change 對全系統 ~50 個 route 做 regex，無 early-exit | O(N×M×P) | change 數與規則數是相乘關係——兩邊同時變多時，耗時是「相乘」等級成長，不是「相加」，規則一多、比對次數就爆炸性成長 | ★ 已證實主戰場 |
| `update_current_config()` | 呼叫外部套件 libyang.xpath_set/del，內部複雜度未確認 | 未確認 | 實測耗時會隨資料量變多而增加，但確切成長速度（是等比例、還是更快）尚未驗證 | 實測非可忽略（3.2s） |

### 關鍵浪費
ADD 400 groups 時，2 萬筆 change 每筆最終只命中 1 個 route，其餘約 49 個 route 的 regex 比對「注定失敗」仍照跑 → 約 196 萬次白工

## 第 5 頁

**Title：修復成效**

### 實測倍數
（交易 1 = 刪除 520 個 single-ap 的小規模測試；交易 2 = 同一次操作觸發連鎖放大後、實際產生 51,779 筆 change 的大規模測試，即第 8 頁「意外發現」的異常放大案例）
- 交易 1（520 筆）：routes_from_changes 0.508s → 0.046s（**~11x**）
- 交易 2（51,779 筆，含連鎖放大）：routes_from_changes 64.295s → 3.577s（**~18x**）
- pre-callback 總時間：交易1 0.576s→0.112s（~5.1x）；交易2 70.955s→10.14s（~7.0x）
- **端到端**（commit 到 apply_ap_group 完成）：交易2 約 78s → 17s（~4.6x）

## 第 6 頁

**Title：解決方案**

### 概念
用 xpath「config 之後第一段節點名」（如 wlan-setting／vrf／bgp）把 ~50 個 route 分桶，每個 change 只掃同 area 候選（實測約 6–10 個），核心比對邏輯（`pattern.search`）一字未改

### 零 side-effect 三點保證
1. 篩選出來的候選名單一定涵蓋所有可能相符的規則，被排除的規則本來就不可能相符，所以不會漏判
2. 無法判別 area 的 route 一律進 wildcard 桶，每個 change 都試 → 不會漏判
3. route 相對順序不變，執行序仍由既有 `deps` 機制決定

### 範圍與驗證
單一檔案 `yams/util/sysrepo.py`；單元測試「黃金比對」+ 兩組實機 reproducer，route 選擇結果 100% 一致

**Title：程式碼 diff 摘要**

### 改動範圍
`yams/util/sysrepo.py`，`routes_from_changes()`

```diff

+     if self._route_index is None:
+         self._build_route_index()
+
      routes = {}
      for change in changes:

                  match = pattern.search(change.xpath)   # ← 核心比對邏輯完全不變
```

### 說明
- 新增兩個輔助方法：`_xpath_area()`（從 xpath 取出 area 節點名）、`_build_route_index()`（啟動後 lazy build 一次 area → routes 索引）
- 改動只有一處：`for route in self.config_routes` → `for route in candidates`，迴圈內文（regex 比對、`routes` dict 寫入）**一字未改**

## 第 9 頁

**Title：風險與意義**

### 重要性
比本次修復更根本，潛在效益可能超過本次全部優化加總，且可與本次修復疊加

### 推測原因（未查證）
single-ap override 刪除後設定回復 default，觸發大量 implicit default 重新計算；或 must/when constraint／leafref 反向關聯連鎖變動

### 風險提示
只要操作觸及大量 single-ap 刪除，即使套用本次修復仍可能因 N 被放大而延遲 → 不建議對外承諾絕對效能上限
