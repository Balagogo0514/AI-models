# YANG Validation 效能稽核簡報大綱(11 頁)— 全庫掃描:揪出重複出現的高成本驗證寫法

報告對象：AE / PM / SVD / CSO / RD
資料來源：`docs/yang-validation-performance.md`（全庫掃描與分類）、`docs/yang-validation-audit-findings.md`（稽核套用紀錄）、`docs/yang-unique.md`（unique 與 ext-cond 用法盤點）、`docs/6WIND-yang-extension.md`（6WIND 自訂 extension 分析）

---

## 第 1 頁

**Title：問題動機**

### 背景

WLAN 模組先前已針對 `wlan-setting` 子樹做過效能調查與修復（詳見 `wlan-setting-yang-speedup.md`）。修復後隨即產生一個問題：這些高成本的 YANG 寫法（重複的唯一性檢查、跨 list 掃描）是 WLAN 模組特有的問題，還是整個 codebase 寫 YANG 時的習慣性寫法？

### 這次掃描要回答的問題

對 repo 內全部 **242 個** `*.yang` 檔案做靜態掃描，統計 `must`、`when`、`leafref` 三種語法的數量與寫法，找出可能拖慢 libyang/sysrepo validation 的模式，並比對是否與 WLAN 案例是同一類問題。

---

## 第 2 頁

**Title：語法成本排序**

### 三種語法的影響力不對等

`leafref` < `when` < `must`，差異來自 libyang/sysrepo 何時、多頻繁重新求值它們。

| 語法 | 求值時機 | 本庫典型成本 | 可否放大 |
|------|----------|--------------|----------|
| `leafref` | schema compile 期解析路徑，執行期常數次 lookup | O(1) / 每個 leafref | 會隨「同一 entry 掛多少個 leafref」線性放大 |
| `when` | 執行期，決定子樹存在與否 | O(1)（本庫皆為簡單 sibling 比較） | 理論上可放大，本庫未觀察到 |
| `must` | 執行期，任意 XPath 邏輯判斷 | O(1) 到 O(n²) / O(n×m)，視寫法而定 | 本庫已出現多處 O(n²) 重複唯一性檢查 |

### 為什麼 must 影響力最大

`must` 是唯一「拿來做任意邏輯判斷」的語法，成本取決於掛在哪種節點上、XPath 掃描範圍多大。全庫真正需要處理的效能債，幾乎都集中在 `must` 的寫法上。

## 第 3 頁

**Title：唯一性檢查的三種寫法比較**

### 同一個目的,三種實作,成本天差地遠

「list 裡的值不可重複」這件事,本庫實際上有三種寫法,成本從免費到 O(n²) 都有:

| 寫法 | 求值機制 | 成本 | 說明 |
|------|----------|------|------|
| `key` | libyang 資料層原生強制,結構層保證,不需要額外邏輯 | 免費(結構本身保證) | list 設計上本來就假設 key 唯一,不用另外寫檢查 |
| `unique` | libyang 內建演算法處理非 key 欄位唯一性 | 比逐筆 XPath 掃描便宜 | 原生 YANG 約束,但全庫只用了 6 處 |
| `must count(...) = 1` | 執行期 XPath,每筆 entry 都重新掃一次同層所有 sibling | O(n²)(list 有 n 筆,每筆各掃一次全部) | 手刻邏輯,無法借用 libyang 原生機制,是三者中最貴的 |

### unique 有一個關鍵限制:只能檢查同一個 list 內部

原生 `unique` 是 YANG 語言規範(RFC 7950)本身的限制,只能比對**同一個 list 底下不同 entry**的欄位值,沒有辦法跨到另一個 list 做比對。如果唯一性需求是「這個值在 list A 和 list B 之間都不能重複」,原生 `unique` 無法表達這種語意,套用下去只會保證各自 list 內部不重複,無法阻擋跨 list 的重複值。

本庫已經有對應跨 list/跨 subtree 唯一性需求的自訂 extension `ext-cond:unique-values`(定義於 `yams/yang/extra-conditions.yang`,目前 9 處實際用法,例如 `vrouter-ike.yang` 的 VPN security-policy 名稱唯一、`vrouter-bgp.yang` 的 community-list 唯一)。判斷該用哪一種的依據很單純:**先確認掃描範圍是不是真的只在同一個 list 內**——是,才能用原生 `unique`;涉及多個 list,要嘛用 `ext-cond:unique-values`,要嘛保留原本的 `must`。

### 這解釋了分類 A 和分類 B 的判斷依據

- **分類 A** 的問題是:欄位明明已經是 `key`(免費保證唯一),卻又多寫一條 `must count()`(O(n²))重複檢查同一件事——這是純粹白付的成本,直接刪除即可。
- **分類 B** 的問題是:欄位是非 key 欄位,唯一性檢查有其必要,但寫成了 `must count()`(O(n²)),其實可以換成原生 `unique`(更便宜),前提是要先確認掃描範圍真的只在同一個 list 內(第 6 頁會說明為什麼這個前提很重要)。

## 第 4 頁

**Title：全庫掃描結果**

### 全域統計

| 項目 | 數量 | 分布檔案數 |
|------|------|------------|
| `must` | 394 | 79 |
| `when` | 47 | 16 |
| `leafref` | 230 | 45 |
| 含 `count(...)` 的 `must` | ~71 檔案命中 | 71 |
| 逐筆唯一性 XPath（`count(...current()...) = 1`） | 22 處 | 15 |

### 好消息

全庫沒有出現 `//`（descendant-or-self）或 `deref()`，代表沒有最貴的一類「全樹掃描」寫法。成本集中在少數重複出現的 XPath pattern，不是總數本身造成的問題。

## 第 5 頁

**Title：成本分類總覽**

掃描結果依成本來源分成 8 類，逐一判斷是否可安全修改：

| 分類 | 內容 | 處理結果 |
|------|------|----------|
| A | 與 `key` 重複的唯一性檢查 | ✅ 14 處已刪除 |
| B | 非 key 欄位唯一性，可改 `unique` | 部分套用（詳見第 7 頁） |
| C | 真正的跨子樹/foreign-key 存在性檢查 | 多數保留；4+1 處確認已作廢 |
| D | 已停用、疑似無替代實作的 must | 正確性風險，待模組負責人決策 |
| E | 大量 leafref 集中單一 rule list（fan-out） | 待實測，暫不改動 |
| G | 掛在單例 container 上疑似恆真的 must | 1 處確認恆真但與效能無關，未套用 |
| H | 可改用原生 `max-elements` | 目標模組已無人使用，不執行 |

這是本次掃描最大的價值：**不是每個「看起來能優化」的項目都值得動**，每一類都要先驗證才能決定。

## 第 6 頁

**Title：分類 A — 已完成的修復**

### 典型模式

```yang
list foo {
  key "name";
  leaf name {
    must "count(../../*[name=current()]) = 1" {
      error-message "This name is duplicated.";
    }
  }
}
```

`key "name"` 本身已由 libyang 在資料層強制唯一，這條 `must` 對任何合法輸入必為真，是白付的重複計算，成本接近 O(n²)。

### 已套用範圍與成效

逐一確認 14 處 list 都確實有對應的 `key`（aaa server 各類型、address/service/schedule/user object、geoip rule），確認無外部工具依賴其自訂錯誤訊息文字後，**14 處已全數刪除**，不改變任何設定的接受/拒絕結果。

## 第 7 頁

**Title：分類 B — 同類型不同結論**

### 已套用：`pppoe/link-interface`

`pppoe` list 用 `count()` 檢查 `link-interface` 欄位不可重複。確認欄位為 `mandatory true`、predicate 只掃自己這個 list 後，改寫成原生 `unique "link-interface";`，成本更低且行為等價。**已套用**。

### 不執行：`ike-zyext/id`

表面上是同一種模式，但追到真正使用點才發現：`zyxel-pre-shared-key`、`pre-shared-key`、`eap-key` 三個 **sibling list 各自都有自己的 `leaf-list id`**，原本的 `count()` 掃的是三個 list 加總的**跨 list**唯一性。而原生 `unique`（見第 3 頁）依語言規範**只能檢查同一個 list 內部**，沒有能力表達「三個 list 之間都不能重複」這種語意——若直接改成同一 list 上的 `unique`，會默默放行跨 list 的重複值——是功能倒退，不是效能優化。**不執行**，需要 IKE 模組負責人確認三個 list 互斥的意圖是否還成立，再評估是否改寫成本庫既有的跨 list extension `ext-cond:unique-values`。

### 這個案例的意義

兩處寫法表面相同，一個能安全改、一個不能改，差別只在「有沒有追到實際使用點確認 XPath 掃描範圍」。這說明這類優化不能靠 pattern-matching 批次處理，必須逐一驗證。

## 第 8 頁

**Title：排除與擱置項目**

### 已確認排除的項目

- **分類 C（4+1 處，routing l3vrf 存在性檢查）**：追查後發現全部掛在 `status deprecated; config false;` 的唯讀子樹底下，已作廢，不需要當成「必須保留的業務邏輯」處理。
- **分類 G（1 處，`network-tool-diagnostics.yang`）**：結構上恆真，是死代碼，但因為本來就是 O(1)、從未造成效能熱點，判定與這次效能優化任務**無關**，維持現狀不動。
- **分類 H（`vrouter-aaa.yang` tacacs 上限）**：改法本身沒有風險，但確認目標模組已無人使用，優化不會帶來任何實際效益，不執行。

### 需要後續人工決策的項目

- **分類 D**：`vrouter-routing.yang` 有一段已被整段註解掉的 `must`（「一個 interface 只能被一個 routing instance 使用」），repo 內找不到對應的 Python 端替代檢查——這條規則目前可能完全沒有被強制執行，是**正確性風險**，需要 routing 模組負責人確認是否還需要。

## 第 9 頁

**Title：結構性根因**

### augment 是成本疊加的機制

`augment`（553 處，169 檔）本身零成本，但它決定了「哪些 `must`/`leafref` 最終會落在同一棵共用子樹下」。WLAN 案例（多個大 list augment 到同一棵樹）與分類 E（secure-policy/bwm 單筆規則掛十幾個 leafref）本質上都是 augment 造成的成本疊加效應。

### unique 陳述式嚴重用得太少

`unique` 是 YANG 原生的「list 內非 key 欄位唯一性」約束，比手寫 `count()` XPath 掃描便宜，全庫目前只用了 **6 處**，對比分類 A/B 找到的 16 處本該用 `unique` 卻用了昂貴 `must count()` 的案例，說明團隊習慣用 `must` 手刻邏輯，而非優先找原生 YANG 約束。

## 第 10 頁

**Title：6WIND Extension 中真正幫得上效率的部分**

### 三組 6WIND 自訂 extension,只有一組會影響驗證效能

6WIND 在 `yams/yang/` 定義了三組自訂 YANG extension，但**只有 `ext-cond`（`extra-conditions`）會實際影響 sysrepo/libyang 的驗證結果**；另外兩組明確不影響效能，拿掉不會讓任何一筆設定變快或變慢：

| 組別 | 用途 | 是否影響驗證效能 |
|------|------|------------------|
| `vr-ext`（`vrouter-extensions`） | 餵給 netconf-cli 的呈現層 metadata（tab 補全、one-liner 指令、互斥群組等） | 否，純 CLI 呈現層 |
| `vr-api`（`vrouter-api`） | 記錄 YANG 模型相對前版的變更，供版本比對/回溯相容性 review | 否，純 metadata/changelog |
| `ext-cond`（`extra-conditions`） | 補原生 `unique` 表達力不足的唯一性約束 | **是**，真正的 schema constraint |

### ext-cond 三個 extension：補原生 unique 做不到的兩個缺口

| Extension | 用量 | 補的是原生 unique 的哪個缺口 |
|-----------|------|------------------------------|
| `unique-values` | 9 | 原生 `unique` 只能檢查**同一個 list 內部**（見第 3 頁），這個 extension 可以跨 list / 跨 subtree 做唯一性檢查 |
| `unique-tuple` | 11 | 原生 `unique` 依 RFC 7950 §7.8.3.1 會**忽略沒有全部設值的 entry**，這個 extension 把 unset 的 leaf 也納入唯一性判斷 |
| `unique-tuple-default` | 1 | 搭配 `unique-tuple`，leaf 未設定時可指定從別的 XPath 取一個 default 值參與判斷 |

### 對照第 3 頁：完整的唯一性檢查選型順序

同一件「值不可重複」的需求，依情境從便宜到能表達的語意，選型順序是：

1. 欄位是 entry 身分 → `key`（免費，結構層保證）
2. 同一 list 內、非 key 欄位 → 原生 `unique`
3. 跨 list / 跨 subtree → `ext-cond:unique-values`
4. 需要把 unset leaf 也納入判斷 → `ext-cond:unique-tuple`（+ `unique-tuple-default`）

只有最後兩項需要動用 6WIND 自訂 extension；`ike-zyext/id`（第 7 頁）就是候選 2 落空、需要評估改用選項 3 的實例。
