# 企業知識庫：依知識型態分層的架構與選型（功能開發與 issue 排查）

> 資料日期：2026-11-24  
> 範圍：公司內部已有多個不同功能的知識庫（功能開發、issue 排查等）時，**應該建立怎樣的知識庫系統**：分層架構、依知識型態選機制的決策、兩個情境的差異、共同的 metadata 與生命週期、導入順序與要避免的事。  
> 讀法：**【本庫】** 取自本庫已整理的文件（[Enterprise-AI-Integration](Enterprise-AI-Integration.md)、[LLM-Wiki](LLM-Wiki.md)、[Claude-Coredump-Wiki](Claude-Coredump-Wiki.md)）；**【建議】** 是我的設計建議；**【推論】** 是我的類推，沒有直接依據。  
> ⚠️ **這是設計建議，不是驗證過的方案。** 我沒有你們公司的資料（知識庫放在哪、多大、權限怎麼分），沒有實作或實測過整合，**也不指定任何產品**。第 8 節列出需要你先確認的問題，答案會改變結論。

## 先看結論

- **不要把所有知識庫合併成一個，也不要只選一種技術。** 做法是：**保留各知識庫原本的來源與負責人，依「知識型態」選不同的機制，再用統一的入口、權限與 metadata 把它們串起來**（【建議】）。
- **依型態分，不依部門分**：穩定的規格與設計 → RAG；排查經驗與案例 → LLM Wiki ＋ 案件資料庫；即時系統資料與動作 → MCP 或 API 工具；程式碼 → 程式碼搜尋；編號、簽章這類精確比對 → 資料庫或關鍵字搜尋（第 2、4 節）。
- **兩個情境的重點不同**：功能開發要「找得到、依據是權威版本」；issue 排查要「以前發生過嗎、根因是什麼、修好了沒」，重點在累積、版本、狀態與可信度（第 5 節）。
- **共同底座比選哪個技術更重要**：每份知識要有負責人、適用範圍與版本、狀態、來源連結與最後確認日期；沒有負責人與過期機制，任何知識庫都會腐爛（第 6 節）。
- **導入先做一個場景**：我傾向 issue 排查（重複問題多、可量測），用最小版本與真實問題評測，再擴充（第 7 節）。
- **最大的風險**：AI 自動寫入而沒有人審閱，錯誤會被累積並被後續引用；以及忽略權限，摘要頁這類衍生內容也可能洩漏原文權限外的資訊（第 9 節）。

## 1. 問題與原則

「知識庫」這個詞涵蓋很多不同的東西：規格文件、設計決策、已知問題與根因、runbook、ticket 狀態、程式碼。它們的**更新節奏、權限、可信度、被查詢的方式**都不同。如果把它們塞進同一個索引，會互相拖累。

【本庫】[Enterprise-AI-Integration](Enterprise-AI-Integration.md) 的原則是：**由輕到重，上一層解決不了才往下一層**（提示詞與工作流 → RAG → 工具與 MCP → Agent → 微調 → 自建模型服務）。本文把它延伸到知識庫：**先確認每份知識是什麼型態，再選最輕的、夠用的機制。**

## 2. 知識型態與建議機制

![圖：五種知識型態對應的建議機制：穩定規格用 RAG、排查經驗用 LLM Wiki 加案件資料庫、即時系統用 MCP 或 API 工具、程式碼用程式碼搜尋、精確比對用資料庫或關鍵字搜尋](figures/enterprise-kb-types.svg)

| 知識型態 | 典型內容 | 建議機制 | 依據 |
|---|---|---|---|
| **穩定的規格與設計** | 需求、設計文件、API 與元件慣例、決策紀錄 | **RAG**：hybrid 檢索、依權限過濾、附引用 | 【本庫】答案要依據內部文件時用 RAG；資料更新只要重建索引，不必重訓 |
| **排查經驗與案例** | 已知問題、根因、哪個版本修好、症狀對照、runbook | **LLM Wiki ＋ 案件資料庫**，人工核准才寫入 | 【本庫】知識會累積、會過時，錯誤會被累積，要人審閱（[LLM-Wiki](LLM-Wiki.md)）；實作範例見 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md) |
| **即時系統資料與動作** | ticket 狀態、build、部署、日誌、監控；建單、加註解 | **MCP 或 API 工具**，先唯讀再逐級放寬 | 【本庫】答案是「現在的值」或要執行動作時，用工具而不是 RAG；權限階梯 L1–L4 |
| **程式碼** | repo、commit、blame | **程式碼搜尋與 repo 工具**（例如讓 coding agent 直接讀） | 【推論】程式碼隨時在變，不適合當成預先建好的文件索引；【本庫】接程式碼庫時用沙箱中的 coding agent，成果走 PR 與審查 |
| **編號、簽章、錯誤碼的精確比對** | issue 編號、crash 簽章、錯誤碼 | **資料庫或關鍵字搜尋** | 【本庫】hybrid 中關鍵字檢索對精確字串通常較準；這類查詢不需要 RAG，也不需要 wiki |

一份知識**可以同時被多種機制使用**，例如案件資料庫負責精確比對，wiki 負責可讀、可累積的敘述（【建議】）。

## 3. 分層架構

![圖：企業知識庫的分層架構：使用者與 AI 應用，經入口與閘道層，進入 RAG、LLM Wiki 加案件資料庫、MCP 或 API 工具、程式碼搜尋四種機制，各自連到原本的來源；共同底座橫跨所有層](figures/enterprise-kb-architecture.svg)

由上到下：

1. **使用者與 AI 應用**：問答入口、Claude Code 或 IDE、Jira 等內部應用。
2. **入口與閘道層**：【本庫】不要讓每個應用各自拿金鑰直連模型，在中間放一層統一入口，集中處理身分驗證與權限、金鑰管理、配額與限流、日誌與稽核、敏感資料遮罩、模型路由與備援、快取。**知道是誰在問，才能依身分過濾資料。**
3. **機制層**：四種機制各自負責一種型態（第 2 節）。【本庫】常見組合是把 RAG 檢索服務包成**唯讀的 MCP server**，與其他 MCP server（即時查詢、動作）一起交給 Agent，由 Agent 決定何時呼叫哪一個；**不建議**用 MCP 逐一呼叫工具去讀大量非結構化文件，又慢又貴。該文件把這點標為 🛠（建議，業界常見做法，不是 MCP 規定的）。
4. **來源層**：每個知識庫**保留原本的來源與負責人**，不搬進同一個庫；機制層只建索引或呼叫介面。
5. **共同底座**（橫跨所有層）：metadata、權限、評測集與回歸、過期審查（第 6 節）。

**權限怎麼帶**（【本庫】，該文件標為 🛠 建議）：優先讓 AI 以**使用者的身分**存取資料（使用者看不到的，AI 也看不到）；只有必要時才用權限受限的服務帳號。RAG 要把**文件級或欄位級的 ACL 隨 metadata 一起進索引**，檢索時依身分過濾；模型不會自己守權限，漏進 prompt 的內容就可能被問出來。

## 4. 選型決策

![圖：選型決策圖：現在的值或動作用 MCP 或 API 工具；程式碼用程式碼搜尋；精確比對用資料庫或關鍵字搜尋；會累積需審閱的經驗知識且量中小用 LLM Wiki 加案件資料庫；大量非結構化文件用 RAG](figures/enterprise-kb-choose.svg)

各機制的主要風險（【本庫】RAG 與 MCP 的對照，加上 LLM-Wiki 的整理）：

| 機制 | 適合 | 主要風險 |
|---|---|---|
| RAG | 大量非結構化文件（規章、手冊、知識庫）；預先建索引，有新鮮度延遲；只讀 | 權限外洩、引用舊資料 |
| MCP／API 工具 | 即時查詢系統與執行動作；通常直接呼叫來源，取得當下的值 | 過大的權限、prompt injection、寫入誤操作 |
| LLM Wiki ＋ 案件資料庫 | 會累積、需要人審閱的經驗知識；人也能直接讀 | LLM 的錯誤被寫進頁面並被引用；過時；摘要頁是衍生內容，可能洩漏權限外資訊（【推論】） |
| 程式碼搜尋 | 隨時在變的程式碼 | 權限、密鑰與執行環境隔離 |

**LLM Wiki 的規模限制**：【本庫】gist 只談到「約 100 份資料、數百頁」的規模，且用 `index.md` 即可；你們若遠大於此，那一塊要另外評估，可能要搭配搜尋或 RAG（見 [LLM-Wiki](LLM-Wiki.md) 第 3 節的比較）。

## 5. 兩個情境：功能開發與 issue 排查

| | 功能開發 | issue 排查 |
|---|---|---|
| **需要什麼知識** | 規格、設計決策、API 與元件慣例、既有程式碼脈絡、「為什麼這樣做」 | 已知問題與根因、症狀到原因、版本與修復狀態、runbook、目前的系統狀態 |
| **主要機制** | RAG（規格與設計）＋ 程式碼搜尋 | LLM Wiki ＋ 案件資料庫 ＋ MCP（即時狀態）＋ RAG（runbook）＋ 程式碼搜尋 |
| **重點** | 找得到、讀得懂、依據是**權威版本** | **累積、版本與狀態、可信度**：以前發生過嗎、修好了沒、這個版本還會發生嗎 |
| **主要風險** | 引用舊版本、權限、找不到 | 錯誤結論被累積、已修復的版本回歸、過時 |
| **成功指標**（【建議】，數字由你們定） | 找到正確文件的比例、引用正確率 | 命中已知問題的比例、誤命中率、解決時間 |

【推論】功能開發也有經驗型知識（踩過的坑、設計取捨的背景）；這部分同樣可以用 wiki 累積，但**穩定的規格與決策紀錄仍適合 RAG**。

### 5.1 issue 排查的查詢流程（設計構想）

![圖：issue 排查的查詢流程：工程師提問，閘道層驗證身分，並行查案件資料庫與 wiki、MCP 工具、RAG、程式碼搜尋，彙整答案附引用；已知問題連到根因頁，否則分析、人工核准、寫入 wiki](figures/enterprise-kb-troubleshoot.svg)

- 並行查四路，**彙整時附引用與來源連結**（【本庫】可追溯是企業 RAG 的硬性要求之一）。
- **已知問題**：答案連到 wiki 的根因頁；**未知問題**：進入分析，**人工核准後才寫入**，下次就是已知問題。這與 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md) 的 coredump 案例庫流程同一個模式。
- 【推論】這個整合我沒有實作過；coredump 的 wiki 範例只覆蓋「簽章查詢」，不含 MCP、RAG 與程式碼搜尋的串接。

## 6. 共同底座：metadata、生命週期、權限與評測

![圖：每份知識的生命週期：草稿經審閱核准成為已核准；定期確認仍有效；超過期限沒確認進入待複查；確認不再有效就淘汰；右邊是共同欄位](figures/enterprise-kb-lifecycle.svg)

**共同欄位**（【建議】）：負責人（owner）、適用範圍與版本、狀態（草稿、已核准、已淘汰）、來源連結、最後確認日期、權限（誰能看）。**沒有負責人與過期機制，任何知識庫都會腐爛。**

**企業環境的硬性要求**（【本庫】對 RAG 的整理，也適用於這個系統）：

| 要求 | 做法 |
|---|---|
| 權限 | 檢索時依使用者身分過濾；ACL 隨 metadata 進索引 |
| 資料新鮮度 | 增量同步；刪除與修訂要能從索引移除，否則答案會引用已撤銷的規定 |
| 可追溯 | 每個答案附引用並保留來源連結 |
| 稽核紀錄 | 記錄誰在何時問了什麼、用了哪些文件 |
| 資料不外流 | 選用符合合規的部署與服務條款；敏感文件分級 |
| 評估與監控 | 固定評估集、線上回饋、定期回歸測試；資料與模型一變，品質就可能退步 |

**人在迴路**：【本庫】經驗型知識（wiki）要**人工核准才寫入**；接內部系統要**先唯讀**，寫入類能力要有開關與稽核，高風險寫入一律人工審核。

## 7. 導入順序

![圖：導入順序的五個階段與過關條件：盤點、選一個高價值場景、最小版本、評測、擴充與治理](figures/enterprise-kb-rollout.svg)

1. **盤點**：各知識庫放在哪、誰維護、更新頻率、權限模型、能不能送外部 API。
2. **選一個高價值場景**：我傾向 issue 排查（【推論】重複問題多、命中率與解決時間可以量，且本庫已有 coredump 的設計與範例可參考）；你們的優先順序可能不同。
3. **最小版本**：該場景對應的機制，只接 1–2 個知識庫，不先整合所有庫。
4. **評測**：用真實問題建評測集，量命中率與錯誤率；換模型或資料前回歸（【本庫】）。
5. **擴充與治理**：擴到功能開發；補核准流程、權限、過期審查與資料外送政策。

**沒有工期估計**：我沒有你們的人力與資料量，不編數字；過關條件的門檻由你們決定。

## 8. 需要你先確認的事

這些答案會改變結論：

1. **現有知識庫**在哪些系統（Wiki、文件庫、Git、Jira、其他），各有多少內容、多久更新一次？
2. **權限**怎麼分（依專案、部門、還是個人）？有沒有資料**不能送外部 API**？
3. **使用者**是誰、有多少人？最大的痛點是**找不到、過時、還是重複問**？
4. **既有的搜尋或 AI 工具**是什麼？能不能沿用，還是要整合？
5. **排查經驗**目前記在哪裡？有沒有結構化的案件紀錄（簽章、版本、狀態）？
6. **誰能當負責人與核准者**？沒有人負責，wiki 與生命週期都無法運作。

## 9. 要避免的事

![圖：要避免的五件事與對策（另有第 6 項影子 AI，見下方文字）：全部塞進同一個向量庫、AI 自動寫入沒人審閱、忽略權限、沒有負責人與過期機制、一次做完](figures/enterprise-kb-pitfalls.svg)

1. **把所有內容塞進同一個向量庫**：型態、更新節奏與權限不同，會互相拖累（【建議】）。
2. **讓 AI 自動寫入而沒有人審閱**：錯誤會被累積並被後續引用（【本庫】[LLM-Wiki](LLM-Wiki.md)）。
3. **忽略權限**：模型不會自己守權限（【本庫】）；摘要頁是衍生內容，也要控管。
4. **沒有負責人與過期機制**：知識庫會腐爛（【建議】）。
5. **一次做完**：先一個場景，由輕到重（【本庫】）。
6. **影子 AI**（圖外補充）：沒有核准的入口與政策，員工會自己用未受管控的工具（【本庫】治理）。
