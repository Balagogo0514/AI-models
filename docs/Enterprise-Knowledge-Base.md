# 企業知識庫：依知識型態分層的架構與選型（功能開發與 issue 排查）

> 資料日期：2026-11-24  
> 範圍：公司內部已有多個不同功能的知識庫（功能開發、issue 排查等）時，**應該建立怎樣的知識庫系統**：分層架構、依知識型態選機制的決策、兩個情境的差異、共同的 metadata 與生命週期、導入順序與要避免的事。  
> 讀法：**【本庫】** 取自本庫已整理的文件（[Enterprise-AI-Integration](Enterprise-AI-Integration.md)、[LLM-Wiki](LLM-Wiki.md)、[Claude-Coredump-Wiki](Claude-Coredump-Wiki.md)）；**【原文】** 是 Karpathy 的 LLM Wiki gist（代理人讀取）；**【二手】** 是搜尋結果摘要（我沒開啟原文）；**【實作】** 是用真實 `gdb`、`git` 與 mock 測過的 coredump 範例；**【建議】** 是我的設計建議；**【推論】** 是我的類推，沒有直接依據。  
> ⚠️ **這是設計建議，不是驗證過的方案。** 我沒有你們公司的資料（知識庫放在哪、多大、權限怎麼分），沒有實作或實測過整合，**也不指定任何產品**。第 9 節列出需要你先確認的問題，答案會改變結論。

## 先看結論

- **不要把所有知識庫合併成一個，也不要只選一種技術。** 做法是：**保留各知識庫原本的來源與負責人，依「知識型態」選不同的機制，再用統一的入口、權限與 metadata 把它們串起來**（【建議】）。
- **依型態分，不依部門分**：穩定的規格與設計 → RAG；排查經驗與案例 → LLM Wiki ＋ 案件資料庫；即時系統資料與動作 → MCP 或 API 工具；程式碼 → 程式碼搜尋；編號、簽章這類精確比對 → 資料庫或關鍵字搜尋（第 2、4 節）。
- **兩個情境的重點不同**：功能開發要「找得到、依據是權威版本」；issue 排查要「以前發生過嗎、根因是什麼、修好了沒」，重點在累積、版本、狀態與可信度（第 6 節）。
- **排查經驗用 LLM Wiki 累積，但要人審閱**（第 5 節）：知識在匯入時整理成頁面並持續維護；建好之後仍需要 AI（新案件分析、選用的頁面改寫）與人（核准不能省）；我們的實作把機械工作交給程式，沒有 AI 時 wiki 仍可讀但不會成長。
- **共同底座比選哪個技術更重要**：每份知識要有負責人、適用範圍與版本、狀態、來源連結與最後確認日期；沒有負責人與過期機制，任何知識庫都會腐爛（第 7 節）。
- **導入先做一個場景**：我傾向 issue 排查（重複問題多、可量測），用最小版本與真實問題評測，再擴充（第 8 節）。
- **最大的風險**：AI 自動寫入而沒有人審閱，錯誤會被累積並被後續引用；以及忽略權限，摘要頁這類衍生內容也可能洩漏原文權限外的資訊（第 10 節）。

## 1. 問題與原則

「知識庫」這個詞涵蓋很多不同的東西：規格文件、設計決策、已知問題與根因、runbook、ticket 狀態、程式碼。它們的**更新節奏、權限、可信度、被查詢的方式**都不同。如果把它們塞進同一個索引，會互相拖累。

【本庫】[Enterprise-AI-Integration](Enterprise-AI-Integration.md) 的原則是：**由輕到重，上一層解決不了才往下一層**（提示詞與工作流 → RAG → 工具與 MCP → Agent → 微調 → 自建模型服務）。本文把它延伸到知識庫：**先確認每份知識是什麼型態，再選最輕的、夠用的機制。**

## 2. 知識型態與建議機制

![圖：五種知識型態對應的建議機制：穩定規格用 RAG、排查經驗用 LLM Wiki 加案件資料庫、即時系統用 MCP 或 API 工具、程式碼用程式碼搜尋、精確比對用資料庫或關鍵字搜尋](figures/enterprise-kb-types.svg)

| 知識型態 | 典型內容 | 建議機制 | 依據 |
|---|---|---|---|
| **穩定的規格與設計** | 需求、設計文件、API 與元件慣例、決策紀錄 | **RAG**：hybrid 檢索、依權限過濾、附引用 | 【本庫】答案要依據內部文件時用 RAG；資料更新只要重建索引，不必重訓 |
| **排查經驗與案例** | 已知問題、根因、哪個版本修好、症狀對照、runbook | **LLM Wiki ＋ 案件資料庫**，人工核准才寫入 | 【本庫】知識會累積、會過時，錯誤會被累積，要人審閱（[LLM-Wiki](LLM-Wiki.md)）；實作範例見 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md) |
| **即時系統資料與動作** | ticket 狀態、build、部署、日誌、監控；建單、加註解 | **MCP 或 API 工具**，先唯讀再逐級放寬 | 【本庫】答案是「現在的值」或要執行動作時，用工具而不是 RAG；權限階梯 L1–L4 |
| **程式碼** | repo、commit、blame | **程式碼搜尋與 repo 工具**（例如讓 coding agent 直接讀） | 【推論】程式碼隨時在變，不適合當成預先建好的文件索引；【本庫】接程式碼庫時用沙箱中的 coding agent，成果走 PR 與審查 |
| **編號、簽章、錯誤碼的精確比對** | issue 編號、crash 簽章、錯誤碼 | **資料庫或關鍵字搜尋** | 【本庫】hybrid 中關鍵字檢索對精確字串通常較準；這類查詢不需要 RAG，也不需要 wiki |

一份知識**可以同時被多種機制使用**，例如案件資料庫負責精確比對，wiki 負責可讀、可累積的敘述（【建議】）。

## 3. 分層架構

![圖：企業知識庫的分層架構：使用者與 AI 應用，經入口與閘道層，進入 RAG、LLM Wiki 加案件資料庫、MCP 或 API 工具、程式碼搜尋四種機制，各自連到原本的來源；共同底座橫跨所有層](figures/enterprise-kb-architecture.svg)

由上到下：

1. **使用者與 AI 應用**：問答入口、Claude Code 或 IDE、Jira 等內部應用。
2. **入口與閘道層**：【本庫】不要讓每個應用各自拿金鑰直連模型，在中間放一層統一入口，集中處理身分驗證與權限、金鑰管理、配額與限流、日誌與稽核、敏感資料遮罩、模型路由與備援、快取。**知道是誰在問，才能依身分過濾資料。**
3. **機制層**：四種機制各自負責一種型態（第 2 節）。【本庫】常見組合是把 RAG 檢索服務包成**唯讀的 MCP server**，與其他 MCP server（即時查詢、動作）一起交給 Agent，由 Agent 決定何時呼叫哪一個；**不建議**用 MCP 逐一呼叫工具去讀大量非結構化文件，又慢又貴。該文件把這點標為 🛠（建議，業界常見做法，不是 MCP 規定的）。
4. **來源層**：每個知識庫**保留原本的來源與負責人**，不搬進同一個庫；機制層只建索引或呼叫介面。
5. **共同底座**（橫跨所有層）：metadata、權限、評測集與回歸、過期審查（第 7 節）。

**權限怎麼帶**（【本庫】，該文件標為 🛠 建議）：優先讓 AI 以**使用者的身分**存取資料（使用者看不到的，AI 也看不到）；只有必要時才用權限受限的服務帳號。RAG 要把**文件級或欄位級的 ACL 隨 metadata 一起進索引**，檢索時依身分過濾；模型不會自己守權限，漏進 prompt 的內容就可能被問出來。

## 4. 選型決策

![圖：選型決策圖：現在的值或動作用 MCP 或 API 工具；程式碼用程式碼搜尋；精確比對用資料庫或關鍵字搜尋；會累積需審閱的經驗知識且量中小用 LLM Wiki 加案件資料庫；大量非結構化文件用 RAG](figures/enterprise-kb-choose.svg)

各機制的主要風險（【本庫】RAG 與 MCP 的對照，加上 LLM-Wiki 的整理）：

| 機制 | 適合 | 主要風險 |
|---|---|---|
| RAG | 大量非結構化文件（規章、手冊、知識庫）；預先建索引，有新鮮度延遲；只讀 | 權限外洩、引用舊資料 |
| MCP／API 工具 | 即時查詢系統與執行動作；通常直接呼叫來源，取得當下的值 | 過大的權限、prompt injection、寫入誤操作 |
| LLM Wiki ＋ 案件資料庫 | 會累積、需要人審閱的經驗知識；人也能直接讀 | LLM 的錯誤被寫進頁面並被引用；過時；摘要頁是衍生內容，可能洩漏權限外資訊（【推論】） |
| 程式碼搜尋 | 隨時在變的程式碼 | 權限、密鑰與執行環境隔離 |

**LLM Wiki 的規模限制**：【原文】gist 只談到「約 100 份資料、數百頁」的規模，且用 `index.md` 即可；你們若遠大於此，那一塊要另外評估，可能要搭配搜尋或 RAG（見第 5.3、5.6 節與 [LLM-Wiki](LLM-Wiki.md) 第 3 節的比較）。

## 5. 經驗層：LLM Wiki 的運作（排查經驗與案例）

第 2 節把「排查經驗與案例」對應到 **LLM Wiki ＋ 案件資料庫**。本節整合 [LLM-Wiki](LLM-Wiki.md) 的內容，說明它是什麼、怎麼運作、在企業架構裡的位置、建好之後誰做什麼、什麼時候不適合。**標記**：**【原文】** 是 Karpathy 的 gist（2026-04-04），由代理人讀取，gist 本文為逐字讀取，留言串只有摘要，我沒有親自開啟；**【二手】** 是搜尋結果的摘要，我沒有開啟原文；**【實作】** 是 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md)（用真實 `gdb`、`git` 與 mock 測過）。

### 5.1 是什麼：一個設計模式，不是軟體

![圖：LLM Wiki 的三層：原始資料（唯讀、你提供）、wiki（LLM 擁有並維護）、schema（規範 LLM 怎麼維護）](figures/llm-wiki-layers.svg)

【原文】一般用 LLM 處理文件（RAG）時，模型每次都從原始檔重新找、重新推導，**知識不會累積**；LLM Wiki 讓 LLM 在你和原始資料之間，**持續建立並維護一組互相連結的 markdown 頁面**，「the wiki is a persistent, compounding artifact」。gist 自稱是「intentionally abstract」的想法，**沒有給固定的目錄結構**，依領域而定。

| 層 | 內容 | 誰負責 |
|---|---|---|
| **原始資料（raw）** | 文章、論文、資料檔；**唯讀**，是事實來源 | 你提供 |
| **wiki** | LLM 產生的 markdown：摘要、實體與概念頁、比較、總覽，以及 `index.md`、`log.md`；就是一個 git repo | LLM 擁有並維護 |
| **schema** | 一份設定文件，如 `CLAUDE.md` 或 `AGENTS.md`，規定結構、慣例與工作流程；gist 稱它是「the key configuration file」 | 規範 LLM 如何維護 wiki |

### 5.2 三個操作：ingest、query、lint

![圖：三欄：ingest 匯入、query 查詢、lint 健檢的步驟](figures/llm-wiki-ops.svg)

- **Ingest（匯入）**：你放入新資料；LLM 讀它、與你討論，寫摘要頁，更新 index 與相關頁面，在 log 加一筆；**一份資料可能動到 10–15 頁**（【原文】）。
- **Query（查詢）**：LLM 讀 `index.md` 找到頁面再回答，附引用；**好的答案可以存回 wiki**，知識因此累積（【原文】）。
- **Lint（健檢）**：定期檢查矛盾、過時說法、孤立頁面、缺少的概念與交叉引用（【原文】）。
- **兩個輔助檔**（【原文】）：`index.md` 是內容導向的目錄（每頁一行摘要），gist 說在「約 100 份資料、數百頁」的規模下可行；`log.md` 是只增不改的時間紀錄，建議用一致的前綴如 `## [2026-04-02] ingest | 標題`，方便 `grep`。

### 5.3 與 RAG 的差別

![圖：RAG 在提問時才檢索與推導，不累積；LLM Wiki 在匯入時就編譯成頁面並持續維護，好答案存回 wiki](figures/llm-wiki-vs-rag.svg)

差別在**知識什麼時候被整理**：RAG 在查詢時檢索 chunk 並現場推導；LLM Wiki 在匯入時就整理成頁面並持續維護（【原文】）。**兩者互補，不是取代**（【二手】）。逐項比較見 [LLM-Wiki 第 3.2 節](LLM-Wiki.md)，與本文最相關的幾項：

| 面向 | RAG | LLM Wiki |
|---|---|---|
| 知識會累積嗎 | 不會，每次重來 | 會，好答案存回 |
| 權限 | 檢索時依身分過濾（【本庫】） | gist 沒有討論；摘要頁是衍生內容，可能洩漏權限外資訊（【推論】） |
| 可追溯 | 可引用 chunk 原文 | 引用的是 LLM 改寫過的頁面，要靠每頁標註來源（【推論】） |
| 主要錯誤風險 | 檢索漏掉或檢錯 | 整理錯誤被寫進頁面並被引用而累積（【推論】） |
| 規模 | 大量文件 | gist 只談到約 100 份資料、數百頁 |
| 人能否直接讀 | 索引是黑箱（【推論】） | 就是 markdown 與 git 歷史（【原文】） |

### 5.4 在企業知識庫中的位置

![圖：經驗層在企業知識庫中的位置：ticket、事故檢討、runbook、分析報告經 ingest（AI 分析、人工核准才寫入）進入 wiki 與案件資料庫；schema 規範匯入；使用者經閘道層查詢；定期 lint](figures/enterprise-kb-wiki-layer.svg)

【建議】把 wiki 當成「排查經驗」的**可讀、可累積的敘述層**，與結構化的案件資料庫並存：

| 頁面型態（可泛化） | 內容 | coredump 範例（【實作】） |
|---|---|---|
| 問題或症狀頁 | 一種問題的特徵、出現過的案件、對應的根因 | 簽章頁（signal ＋ 最上面的函式） |
| 根因頁 | 根因說明、證據、影響版本、狀態與修復版本 | 根因頁（含 `evidence_id`、`status`、`fixed_in`） |
| 元件或模組頁 | 該元件的已知問題清單 | 模組頁 |
| 案件頁 | 一個 ticket 的分析摘要與連結 | 案件頁 |
| `index.md`、`log.md` | 目錄與時間紀錄 | 由程式維護，不交給模型 |

**分工**：案件資料庫負責**精確比對**（簽章、版本、狀態，可程式查詢）；wiki 負責**敘述與關聯**（根因是什麼、哪些版本修好、有哪些相關案件）。【實作】範例把機械工作（frontmatter、連結、index、log、git commit、簽章比對、機械 lint）交給**程式**，**模型只負責改寫根因頁的敘述，且輸出要通過把關**（保留所有證據 ID、不得出現「已確認根因」、長度不暴增）。

**人在迴圈**（【實作】）：AI 分析後只放進待審區（`propose`），**人工核准才寫進 wiki**（`approve`）；已修復的版本又出現時，查詢會判成 `regression`，不能當成已知問題帶過。**不要為了省事自動核准**，否則錯誤會被累積（【建議】）。

**限制**：coredump 範例只實作了**簽章查詢**；本節的整合（來源是 ticket、事故檢討、runbook，查詢經閘道層與 MCP、RAG 串接）是**設計構想，沒有實作過**。

### 5.5 建好之後：人、AI、程式怎麼分工

![圖：人、AI、程式三方分工，以及一個案件的交接：程式查 wiki，沒命中才由 AI 分析，人審閱核准，程式寫入](figures/llm-wiki-roles.svg)

**建好之後仍然需要 AI，但需要的程度取決於設計；人則一直都需要。**

- **原模式**（【原文】）：你挑資料、提問、審閱；LLM 整理、交叉引用、歸檔與維護，三個操作都由 LLM 執行；gist 說人類維護 wiki 失敗，是因為維護成本太高，LLM 讓這個成本「近乎零」。所以按原模式，AI 是長期的維護者。
- **我們的實作**（【實作】）把機械工作交給程式，**AI 只在「沒命中的新案件分析」與（選用的）根因頁改寫時需要**；**核准、駁回、標記已修復要人，不是 AI**。
- **實作的缺口**（誠實標明）：沒有做**語意 lint**（兩段敘述是否矛盾）、也沒有做**自然語言問答**（只有簽章查詢）；這兩項在原模式裡由 LLM 做。

![圖：沒有 AI 時：簽章命中、寫入、機械 lint 照常；根因頁敘述降級；新案件退回人工；語意檢查與自然語言問答沒有](figures/llm-wiki-without-ai.svg)

**沒有 AI 時**（【推論】）：wiki 是 markdown 加 git，仍可讀可改，只是不會自己成長；命中既有簽章、寫入與機械 lint 照常；新案件會堆積，頁面敘述退回附加而變長難讀。

![圖：維運節奏：每個案件、每天、每週或每月、改模型或規則時、規模變大時，各由誰做什麼](figures/llm-wiki-cadence.svg)

**維運節奏**（【建議】，沒有長期運作的實測）：每個案件由程式查簽章、沒命中才請 AI 分析、人核准、程式寫入；每天程式跑 lint、人處理 error；每週或每月人與 AI 一起看 warn 與 info、清理待審區、檢討誤命中與漏命中；改模型、prompt 或規則時用案例集回歸；規模變大時檢討 `index.md` 是否夠用。**AI 用量隨命中率下降**是推論，沒有實際用量數據。

### 5.6 什麼情況適合，以及風險

| 情況 | 判斷 |
|---|---|
| 資料約 100 份、數百頁 | 適合（【原文】用 index 即可，不需要 embedding 式 RAG） |
| 資料量遠大於此 | 要評估，可能要搭配搜尋或 RAG；我沒有資料 |
| 要即時反映來源最新狀態 | 要承擔重新匯入的落差（【二手】） |
| 答案要可追溯、可稽核 | 適合：保留原始資料與 log，頁面引用來源 |
| 沒有人審閱、錯誤會累積 | **不建議**（【推論】） |

主要風險（【建議】與【推論】）：**錯誤會被累積**；**過時**（來源更新後 wiki 不會自動跟上，要靠 lint 與重新匯入，【二手】）；**矛盾與淘汰**（留言串提到尚未解決，我只看到摘要）；**成本**（一次 ingest 動到 10–15 頁，我沒有估算）；**安全**（外部資料交給有寫入權限的 agent，要注意 prompt injection，schema 要寫明資料是不可信輸入並限制只能寫 wiki 目錄）；**權限**（摘要頁是衍生內容）；社群實作良莠不齊（【二手】說已有 30 多個，我沒確認）。

## 6. 兩個情境：功能開發與 issue 排查

| | 功能開發 | issue 排查 |
|---|---|---|
| **需要什麼知識** | 規格、設計決策、API 與元件慣例、既有程式碼脈絡、「為什麼這樣做」 | 已知問題與根因、症狀到原因、版本與修復狀態、runbook、目前的系統狀態 |
| **主要機制** | RAG（規格與設計）＋ 程式碼搜尋 | LLM Wiki ＋ 案件資料庫 ＋ MCP（即時狀態）＋ RAG（runbook）＋ 程式碼搜尋 |
| **重點** | 找得到、讀得懂、依據是**權威版本** | **累積、版本與狀態、可信度**：以前發生過嗎、修好了沒、這個版本還會發生嗎 |
| **主要風險** | 引用舊版本、權限、找不到 | 錯誤結論被累積、已修復的版本回歸、過時 |
| **成功指標**（【建議】，數字由你們定） | 找到正確文件的比例、引用正確率 | 命中已知問題的比例、誤命中率、解決時間 |

【推論】功能開發也有經驗型知識（踩過的坑、設計取捨的背景）；這部分同樣可以用 wiki 累積，但**穩定的規格與決策紀錄仍適合 RAG**。

### 6.1 issue 排查的查詢流程（設計構想）

![圖：issue 排查的查詢流程：工程師提問，閘道層驗證身分，並行查案件資料庫與 wiki、MCP 工具、RAG、程式碼搜尋，彙整答案附引用；已知問題連到根因頁，否則分析、人工核准、寫入 wiki](figures/enterprise-kb-troubleshoot.svg)

- 並行查四路，**彙整時附引用與來源連結**（【本庫】可追溯是企業 RAG 的硬性要求之一）。
- **已知問題**：答案連到 wiki 的根因頁；**未知問題**：進入分析，**人工核准後才寫入**，下次就是已知問題。這與 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md) 的 coredump 案例庫流程同一個模式。
- 【推論】這個整合我沒有實作過；coredump 的 wiki 範例只覆蓋「簽章查詢」，不含 MCP、RAG 與程式碼搜尋的串接。

## 7. 共同底座：metadata、生命週期、權限與評測

![圖：每份知識的生命週期：草稿經審閱核准成為已核准；定期確認仍有效；超過期限沒確認進入待複查；確認不再有效就淘汰；右邊是共同欄位](figures/enterprise-kb-lifecycle.svg)

**共同欄位**（【建議】）：負責人（owner）、適用範圍與版本、狀態（草稿、已核准、已淘汰）、來源連結、最後確認日期、權限（誰能看）。**沒有負責人與過期機制，任何知識庫都會腐爛。**

**企業環境的硬性要求**（【本庫】對 RAG 的整理，也適用於這個系統）：

| 要求 | 做法 |
|---|---|
| 權限 | 檢索時依使用者身分過濾；ACL 隨 metadata 進索引 |
| 資料新鮮度 | 增量同步；刪除與修訂要能從索引移除，否則答案會引用已撤銷的規定 |
| 可追溯 | 每個答案附引用並保留來源連結 |
| 稽核紀錄 | 記錄誰在何時問了什麼、用了哪些文件 |
| 資料不外流 | 選用符合合規的部署與服務條款；敏感文件分級 |
| 評估與監控 | 固定評估集、線上回饋、定期回歸測試；資料與模型一變，品質就可能退步 |

**人在迴路**：【本庫】經驗型知識（wiki）要**人工核准才寫入**；接內部系統要**先唯讀**，寫入類能力要有開關與稽核，高風險寫入一律人工審核。

## 8. 導入順序

![圖：導入順序的五個階段與過關條件：盤點、選一個高價值場景、最小版本、評測、擴充與治理](figures/enterprise-kb-rollout.svg)

1. **盤點**：各知識庫放在哪、誰維護、更新頻率、權限模型、能不能送外部 API。
2. **選一個高價值場景**：我傾向 issue 排查（【推論】重複問題多、命中率與解決時間可以量，且本庫已有 coredump 的設計與範例可參考）；你們的優先順序可能不同。
3. **最小版本**：該場景對應的機制，只接 1–2 個知識庫，不先整合所有庫。
4. **評測**：用真實問題建評測集，量命中率與錯誤率；換模型或資料前回歸（【本庫】）。
5. **擴充與治理**：擴到功能開發；補核准流程、權限、過期審查與資料外送政策。

**沒有工期估計**：我沒有你們的人力與資料量，不編數字；過關條件的門檻由你們決定。

## 9. 需要你先確認的事

這些答案會改變結論：

1. **現有知識庫**在哪些系統（Wiki、文件庫、Git、Jira、其他），各有多少內容、多久更新一次？
2. **權限**怎麼分（依專案、部門、還是個人）？有沒有資料**不能送外部 API**？
3. **使用者**是誰、有多少人？最大的痛點是**找不到、過時、還是重複問**？
4. **既有的搜尋或 AI 工具**是什麼？能不能沿用，還是要整合？
5. **排查經驗**目前記在哪裡？有沒有結構化的案件紀錄（簽章、版本、狀態）？
6. **誰能當負責人與核准者**？沒有人負責，wiki 與生命週期都無法運作。

## 10. 要避免的事

![圖：要避免的五件事與對策（另有第 6 項影子 AI，見下方文字）：全部塞進同一個向量庫、AI 自動寫入沒人審閱、忽略權限、沒有負責人與過期機制、一次做完](figures/enterprise-kb-pitfalls.svg)

1. **把所有內容塞進同一個向量庫**：型態、更新節奏與權限不同，會互相拖累（【建議】）。
2. **讓 AI 自動寫入而沒有人審閱**：錯誤會被累積並被後續引用（【本庫】[LLM-Wiki](LLM-Wiki.md)）。
3. **忽略權限**：模型不會自己守權限（【本庫】）；摘要頁是衍生內容，也要控管。
4. **沒有負責人與過期機制**：知識庫會腐爛（【建議】）。
5. **一次做完**：先一個場景，由輕到重（【本庫】）。
6. **影子 AI**（圖外補充）：沒有核准的入口與政策，員工會自己用未受管控的工具（【本庫】治理）。
