# 企業知識庫：依知識型態分層的架構與選型（功能開發與 issue 排查）

> 資料日期：2026-11-24  
> 範圍：公司內部已有多個不同功能的知識庫（功能開發、issue 排查等）時，**應該建立怎樣的知識庫系統**：分層架構、依知識型態選機制的決策、兩個情境的差異、共同的 metadata 與生命週期、知識回饋整理（回饋怎麼收集、分類、審核、寫回與驗證）、導入順序與要避免的事。  
> 讀法：**【本庫】** 取自本庫已整理的文件（[Enterprise-AI-Integration](Enterprise-AI-Integration.md)、[Claude-Coredump-Wiki](Claude-Coredump-Wiki.md)，以及已併入第 5 節的 LLM Wiki 內容）；**【原文】** 是 Karpathy 的 LLM Wiki gist（代理人讀取）；**【二手】** 是搜尋結果摘要（我沒開啟原文）；**【實作】** 是用真實 `gdb`、`git` 與 mock 測過的 coredump 範例；**【建議】** 是我的設計建議；**【推論】** 是我的類推，沒有直接依據。  
> ⚠️ **這是設計建議，不是驗證過的方案。** 我沒有你們公司的資料（知識庫放在哪、多大、權限怎麼分），沒有實作或實測過整合，**也不指定任何產品**。第 10 節列出需要你先確認的問題，答案會改變結論。

## 先看結論

- **不要把所有知識庫合併成一個，也不要只選一種技術。** 做法是：**保留各知識庫原本的來源與負責人，依「知識型態」選不同的機制，再用統一的入口、權限與 metadata 把它們串起來**（【建議】）。
- **依型態分，不依部門分**：穩定的規格與設計 → RAG；排查經驗與案例 → LLM Wiki ＋ 案件資料庫；即時系統資料與動作 → MCP 或 API 工具；程式碼 → 程式碼搜尋；編號、簽章這類精確比對 → 資料庫或關鍵字搜尋（第 2、4 節）。
- **兩個情境的重點不同**：功能開發要「找得到、依據是權威版本」；issue 排查要「以前發生過嗎、根因是什麼、修好了沒」，重點在累積、版本、狀態與可信度（第 6 節）。
- **排查經驗用 LLM Wiki 累積，但要人審閱**（第 5 節）：知識在匯入時整理成頁面並持續維護；建好之後仍需要 AI（新案件分析、選用的頁面改寫）與人（核准不能省）；我們的實作把機械工作交給程式，沒有 AI 時 wiki 仍可讀但不會成長。
- **共同底座比選哪個技術更重要**：每份知識要有負責人、適用範圍與版本、狀態、來源連結與最後確認日期；沒有負責人與過期機制，任何知識庫都會腐爛（第 7 節）。
- **用過的回饋要整理後寫回，但不能自動寫**：回饋分類、交給負責人、AI 或程式出草稿、**人審核**後寫回並留痕，再用評測集回歸；使用者的修正本身也要查證（第 8 節）。
- **導入先做一個場景**：我傾向 issue 排查（重複問題多、可量測），用最小版本與真實問題評測，再擴充（第 9 節）。
- **最大的風險**：AI 自動寫入而沒有人審閱，錯誤會被累積並被後續引用；以及忽略權限，摘要頁這類衍生內容也可能洩漏原文權限外的資訊（第 11 節）。

## 1. 問題與原則

「知識庫」這個詞涵蓋很多不同的東西：規格文件、設計決策、已知問題與根因、runbook、ticket 狀態、程式碼。它們的**更新節奏、權限、可信度、被查詢的方式**都不同。如果把它們塞進同一個索引，會互相拖累。

【本庫】[Enterprise-AI-Integration](Enterprise-AI-Integration.md) 的原則是：**由輕到重，上一層解決不了才往下一層**（提示詞與工作流 → RAG → 工具與 MCP → Agent → 微調 → 自建模型服務）。本文把它延伸到知識庫：**先確認每份知識是什麼型態，再選最輕的、夠用的機制。**

## 2. 知識型態與建議機制

![圖：五種知識型態對應的建議機制：穩定規格用 RAG、排查經驗用 LLM Wiki 加案件資料庫、即時系統用 MCP 或 API 工具、程式碼用程式碼搜尋、精確比對用資料庫或關鍵字搜尋](figures/enterprise-kb-types.svg)

| 知識型態 | 典型內容 | 建議機制 | 依據 |
|---|---|---|---|
| **穩定的規格與設計** | 需求、設計文件、API 與元件慣例、決策紀錄 | **RAG**：hybrid 檢索、依權限過濾、附引用 | 【本庫】答案要依據內部文件時用 RAG；資料更新只要重建索引，不必重訓 |
| **排查經驗與案例** | 已知問題、根因、哪個版本修好、症狀對照、runbook | **LLM Wiki ＋ 案件資料庫**，人工核准才寫入 | 【本庫】知識會累積、會過時，錯誤會被累積，要人審閱（見第 5 節）；實作範例見 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md) |
| **即時系統資料與動作** | ticket 狀態、build、部署、日誌、監控；建單、加註解 | **MCP 或 API 工具**，先唯讀再逐級放寬 | 【本庫】答案是「現在的值」或要執行動作時，用工具而不是 RAG；權限階梯 L1–L4 |
| **程式碼** | repo、commit、blame | **程式碼搜尋與 repo 工具**（例如讓 coding agent 直接讀） | 【推論】程式碼隨時在變，不適合當成預先建好的文件索引；【本庫】接程式碼庫時用沙箱中的 coding agent，成果走 PR 與審查 |
| **編號、簽章、錯誤碼的精確比對** | issue 編號、crash 簽章、錯誤碼 | **資料庫或關鍵字搜尋** | 【本庫】hybrid 中關鍵字檢索對精確字串通常較準；這類查詢不需要 RAG，也不需要 wiki |

一份知識**可以同時被多種機制使用**，例如案件資料庫負責精確比對，wiki 負責可讀、可累積的敘述（【建議】）。

## 3. 分層架構

![圖：企業知識庫的分層架構：使用者與 AI 應用，經入口與閘道層，進入 RAG、LLM Wiki 加案件資料庫、MCP 或 API 工具、程式碼搜尋四種機制，各自連到原本的來源；共同底座橫跨所有層](figures/enterprise-kb-architecture.svg)

由上到下：

1. **使用者與 AI 應用**：問答入口、Claude Code 或 IDE、Jira 等內部應用。
2. **入口與閘道層**：【本庫】不要讓每個應用各自拿金鑰直連模型，在中間放一層統一入口，集中處理身分驗證與權限、金鑰管理、配額與限流、日誌與稽核、敏感資料遮罩、模型路由與備援、快取。**知道是誰在問，才能依身分過濾資料。**
3. **機制層**：四種機制各自負責一種型態（第 2 節）。【本庫】常見組合是把 RAG 檢索服務包成**唯讀的 MCP server**，與其他 MCP server（即時查詢、動作）一起交給 Agent，由 Agent 決定何時呼叫哪一個；**不建議**用 MCP 逐一呼叫工具去讀大量非結構化文件，又慢又貴。該文件把這點標為 🛠（建議，業界常見做法，不是 MCP 規定的）。
4. **來源層**：每個知識庫**保留原本的來源與負責人**，不搬進同一個庫；機制層只建索引或呼叫介面。
5. **共同底座**（橫跨所有層）：metadata、權限、評測集與回歸、過期審查（第 7 節）。

**權限怎麼帶**（【本庫】，該文件標為 🛠 建議）：優先讓 AI 以**使用者的身分**存取資料（使用者看不到的，AI 也看不到）；只有必要時才用權限受限的服務帳號。RAG 要把**文件級或欄位級的 ACL 隨 metadata 一起進索引**，檢索時依身分過濾；模型不會自己守權限，漏進 prompt 的內容就可能被問出來。

## 4. 選型決策

![圖：選型決策圖：現在的值或動作用 MCP 或 API 工具；程式碼用程式碼搜尋；精確比對用資料庫或關鍵字搜尋；會累積需審閱的經驗知識且量中小用 LLM Wiki 加案件資料庫；大量非結構化文件用 RAG](figures/enterprise-kb-choose.svg)

各機制的主要風險（【本庫】RAG 與 MCP 的對照，加上第 5 節的整理）：

| 機制 | 適合 | 主要風險 |
|---|---|---|
| RAG | 大量非結構化文件（規章、手冊、知識庫）；預先建索引，有新鮮度延遲；只讀 | 權限外洩、引用舊資料 |
| MCP／API 工具 | 即時查詢系統與執行動作；通常直接呼叫來源，取得當下的值 | 過大的權限、prompt injection、寫入誤操作 |
| LLM Wiki ＋ 案件資料庫 | 會累積、需要人審閱的經驗知識；人也能直接讀 | LLM 的錯誤被寫進頁面並被引用；過時；摘要頁是衍生內容，可能洩漏權限外資訊（【推論】） |
| 程式碼搜尋 | 隨時在變的程式碼 | 權限、密鑰與執行環境隔離 |

**LLM Wiki 的規模限制**：【原文】gist 只談到「約 100 份資料、數百頁」的規模，且用 `index.md` 即可；你們若遠大於此，那一塊要另外評估，可能要搭配搜尋或 RAG（見第 5.3、5.6 節）。

## 5. 經驗層：LLM Wiki 的運作（排查經驗與案例）

第 2 節把「排查經驗與案例」對應到 **LLM Wiki ＋ 案件資料庫**。本節整合 Karpathy 的 LLM Wiki 模式（原本的獨立文件 `LLM-Wiki.md` 已併入本節），說明它是什麼、怎麼運作、在企業架構裡的位置、建好之後誰做什麼、什麼時候不適合。**標記**：**【原文】** 是 Karpathy 的 gist（2026-04-04），由代理人讀取，gist 本文為逐字讀取，留言串只有摘要，我沒有親自開啟；**【二手】** 是搜尋結果的摘要，我沒有開啟原文；**【實作】** 是 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md)（用真實 `gdb`、`git` 與 mock 測過）。

### 5.1 是什麼：一個設計模式，不是軟體

![圖：LLM Wiki 的三層：原始資料（唯讀、你提供）、wiki（LLM 擁有並維護）、schema（規範 LLM 怎麼維護）](figures/llm-wiki-layers.svg)

【原文】一般用 LLM 處理文件（RAG）時，模型每次都從原始檔重新找、重新推導，**知識不會累積**；LLM Wiki 讓 LLM 在你和原始資料之間，**持續建立並維護一組互相連結的 markdown 頁面**，「the wiki is a persistent, compounding artifact」。gist 自稱是「intentionally abstract」的想法，**沒有給固定的目錄結構**，依領域而定。

| 層 | 內容 | 誰負責 |
|---|---|---|
| **原始資料（raw）** | 文章、論文、資料檔；**唯讀**，是事實來源 | 你提供 |
| **wiki** | LLM 產生的 markdown：摘要、實體與概念頁、比較、總覽，以及 `index.md`、`log.md`；就是一個 git repo | LLM 擁有並維護 |
| **schema** | 一份設定文件，如 `CLAUDE.md` 或 `AGENTS.md`，規定結構、慣例與工作流程；gist 稱它是「the key configuration file」 | 規範 LLM 如何維護 wiki |

### 5.2 三個操作：ingest、query、lint

![圖：三欄：ingest 匯入、query 查詢、lint 健檢的步驟](figures/llm-wiki-ops.svg)

- **Ingest（匯入）**：你放入新資料；LLM 讀它、與你討論，寫摘要頁，更新 index 與相關頁面，在 log 加一筆；**一份資料可能動到 10–15 頁**（【原文】）。
- **Query（查詢）**：LLM 讀 `index.md` 找到頁面再回答，附引用；**好的答案可以存回 wiki**，知識因此累積（【原文】）。
- **Lint（健檢）**：定期檢查矛盾、過時說法、孤立頁面、缺少的概念與交叉引用（【原文】）。
- **兩個輔助檔**（【原文】）：`index.md` 是內容導向的目錄（每頁一行摘要），gist 說在「約 100 份資料、數百頁」的規模下可行；`log.md` 是只增不改的時間紀錄，建議用一致的前綴如 `## [2026-04-02] ingest | 標題`，方便 `grep`。

### 5.3 與 RAG 的差別

![圖：RAG 在提問時才檢索與推導，不累積；LLM Wiki 在匯入時就編譯成頁面並持續維護，好答案存回 wiki](figures/llm-wiki-vs-rag.svg)

差別在**知識什麼時候被整理**：RAG 在查詢時檢索 chunk 並現場推導；LLM Wiki 在匯入時就整理成頁面並持續維護（【原文】）。**兩者互補，不是取代**（【二手】）。

**逐項比較**

RAG 一欄的描述取自本庫 [Enterprise-AI-Integration](Enterprise-AI-Integration.md) 對企業 RAG 的整理（【本庫】）；LLM Wiki 一欄取自 gist（【原文】）。**沒有標記來源的欄位是我的推論。**

| 面向 | RAG | LLM Wiki |
|---|---|---|
| **整理時機** | 查詢時：檢索相關 chunk，現場推導答案（【原文】） | 匯入時：編譯成頁面，之後持續維護（【原文】） |
| **知識會累積嗎** | 不會，每次提問重來（【原文】稱它為「沒有累積」的基準） | 會，好的答案可以存回 wiki（【原文】） |
| **資料形態** | chunk ＋ 向量索引，常加關鍵字索引（hybrid）（【本庫】） | markdown 頁面 ＋ `index.md`，進 git（【原文】） |
| **檢索方式** | 向量或 hybrid 檢索，再 rerank（【本庫】） | LLM 先讀 `index.md` 找頁面，再讀頁面；gist 說約 100 份資料、數百頁的規模不需要 embedding 式 RAG（【原文】） |
| **規模** | 本庫的企業 RAG 設計以大量內部資料為前提（【推論】） | gist 只談到約 100 份資料、數百頁；更大的我沒有資料 |
| **權限控制** | 檢索時依使用者身分與權限過濾（【本庫】） | gist 沒有討論；摘要頁是衍生內容，可能含有讀者不該看的原文資訊，要自己設計（【推論】） |
| **更新來源後** | 重建或增量更新索引 | 要重新匯入，wiki 與最新事實之間會有落差（【二手】） |
| **可追溯性** | 可引用 chunk 原文 | 引用的是 LLM 改寫過的頁面，要靠每頁標註來源才能回查（【推論】） |
| **主要錯誤風險** | 檢索漏掉或檢錯，答案跟著錯 | 整理錯誤被寫進頁面，並被後續引用而累積（【推論】） |
| **成本落點** | 建索引（embedding）與每次查詢的檢索加生成 | 每次匯入要讀寫多頁（一份資料常動到 10–15 頁，【原文】），查詢只讀少量頁面；我沒有數字（【推論】） |
| **精確字串**（型號、錯誤碼） | hybrid 的關鍵字檢索通常較準（【本庫】） | 靠 `index.md`、`grep` 或 `qmd` 這類本機搜尋（【原文】提到 `qmd`）；精確度我沒驗證 |
| **人能不能直接讀** | 索引是黑箱，只能看回答與引用（【推論】） | 就是人可讀的 markdown 與 git 歷史（【原文】） |

**怎麼選：RAG 還是 LLM Wiki**

![圖：選 RAG 還是 LLM Wiki 的決策圖：只需要精確比對就用資料庫；資料量大或更新頻繁偏向 RAG；需要權限過濾偏向 RAG；需要累積、可讀、有人審閱才用 LLM Wiki](figures/llm-wiki-vs-rag-choose.svg)

【建議】決策圖是依本庫資料與 gist 整理的，**沒有實測比較**：

- **偏向 LLM Wiki**：資料量中小、希望知識能累積、有人審閱、需要人也能直接讀。
- **偏向 RAG**：資料量大、更新頻繁、需要依權限過濾、需要精確引用原文。
- **只需要精確比對**（簽章、錯誤碼、編號）：用資料庫或關鍵字搜尋就夠，兩者都不需要。
- **搭配使用**：二手說法認為兩者互補，例如 wiki 負責整理過的敘述、RAG 負責大量原始文件的檢索；組合的效果我沒驗證。
- **不確定時**：先從簡單做法開始（小量資料甚至可以直接放進 context），再用自己的案例比較。

### 5.4 在企業知識庫中的位置

![圖：經驗層在企業知識庫中的位置：ticket、事故檢討、runbook、分析報告經 ingest（AI 分析、人工核准才寫入）進入 wiki 與案件資料庫；schema 規範匯入；使用者經閘道層查詢；定期 lint](figures/enterprise-kb-wiki-layer.svg)

【建議】把 wiki 當成「排查經驗」的**可讀、可累積的敘述層**，與結構化的案件資料庫並存：

| 頁面型態（可泛化） | 內容 | coredump 範例（【實作】） |
|---|---|---|
| 問題或症狀頁 | 一種問題的特徵、出現過的案件、對應的根因 | 簽章頁（signal ＋ 最上面的函式） |
| 根因頁 | 根因說明、證據、影響版本、狀態與修復版本 | 根因頁（含 `evidence_id`、`status`、`fixed_in`） |
| 元件或模組頁 | 該元件的已知問題清單 | 模組頁 |
| 案件頁 | 一個 ticket 的分析摘要與連結 | 案件頁 |
| `index.md`、`log.md` | 目錄與時間紀錄 | 由程式維護，不交給模型 |

**分工**：案件資料庫負責**精確比對**（簽章、版本、狀態，可程式查詢）；wiki 負責**敘述與關聯**（根因是什麼、哪些版本修好、有哪些相關案件）。【實作】範例把機械工作（frontmatter、連結、index、log、git commit、簽章比對、機械 lint）交給**程式**，**模型只負責改寫根因頁的敘述，且輸出要通過把關**（保留所有證據 ID、不得出現「已確認根因」、長度不暴增）。

**人在迴圈**（【實作】）：AI 分析後只放進待審區（`propose`），**人工核准才寫進 wiki**（`approve`）；已修復的版本又出現時，查詢會判成 `regression`，不能當成已知問題帶過。**不要為了省事自動核准**，否則錯誤會被累積（【建議】）。

**限制**：coredump 範例只實作了**簽章查詢**；本節的整合（來源是 ticket、事故檢討、runbook，查詢經閘道層與 MCP、RAG 串接）是**設計構想，沒有實作過**。

**coredump 的具體流程**（【建議】，設計構想，沒有實作過整合）

![圖：coredump 案例庫的流程：新案件先用簽章查 wiki，命中就引用既有根因頁；沒命中就由 Claude 分析、驗證、人工審閱後 ingest 回 wiki；定期 lint](figures/llm-wiki-coredump.svg)

**流程**（對應上圖）：
1. 新案件先用簽章查 wiki（簽章頁）。**命中**就引用既有根因頁與相關案件；**仍要驗證版本是否相符**，因為同樣的簽章在不同版本可能是不同原因（【建議】）。
2. **沒命中**就走 [Claude-Coredump-Code](Claude-Coredump-Code.md) 的分析流程，產生報告並通過 schema 驗證。
3. **人工審閱後才 ingest**：寫案件頁，更新簽章頁、根因頁、模組頁、`index.md` 與 `log.md`。**錯誤的結論不要被累積**（【建議】）。
4. **定期 lint**：找互相矛盾的根因、沒有證據的論述、已修復版本卻仍標「未修」的頁面、孤立頁（【建議】）。

**與既有設計的關係**：
- **不取代**案件資料庫與 fingerprint 去重：它們負責「精確、可程式查詢」；wiki 負責「可讀、可累積的敘述與關聯」（【建議】）。
- **evidence_id 要保留**：根因頁引用的證據仍要能回查到工具輸出，才不會變成沒有根據的敘述（呼應報告驗證規則）。
- **Jira 回寫**：命中時可以把既有根因頁的連結放進 comment（【建議】）。

**要特別注意**：
- **資料外送與敏感資料**：wiki 頁面是從 dump 的分析衍生的，可能含客戶資料或機密；放在哪、誰能讀、能不能送給外部 API，要依公司政策（見 [Claude-Coredump-Agent](Claude-Coredump-Agent.md) 第 7 節）。
- **成本**：【原文】一份資料的 ingest 可能動到 10–15 頁，每次要讀寫多個頁面；**我沒有估算 token 與費用**，成本模型見該文件第 6 節，要自己代入實測數字。
- **規模**：gist 的規模描述是約 100 份資料、數百頁；案件量遠大於此時能否只靠 `index.md`，我沒有資料。
- **簽章比對**：簽章要怎麼正規化、怎麼避免誤命中，是額外的工程問題，本文沒有處理。

### 5.5 建好之後：人、AI、程式怎麼分工

![圖：人、AI、程式三方分工，以及一個案件的交接：程式查 wiki，沒命中才由 AI 分析，人審閱核准，程式寫入](figures/llm-wiki-roles.svg)

**建好之後仍然需要 AI，但需要的程度取決於設計；人則一直都需要。**

- **原模式**（【原文】）：你挑資料、提問、審閱；LLM 整理、交叉引用、歸檔與維護，三個操作都由 LLM 執行；gist 說人類維護 wiki 失敗，是因為維護成本太高，LLM 讓這個成本「近乎零」。所以按原模式，AI 是長期的維護者。
- **我們的實作**（【實作】）把機械工作交給程式，**AI 只在「沒命中的新案件分析」與（選用的）根因頁改寫時需要**；**核准、駁回、標記已修復要人，不是 AI**。
- **實作的缺口**（誠實標明）：沒有做**語意 lint**（兩段敘述是否矛盾）、也沒有做**自然語言問答**（只有簽章查詢）；這兩項在原模式裡由 LLM 做。

![圖：沒有 AI 時：簽章命中、寫入、機械 lint 照常；根因頁敘述降級；新案件退回人工；語意檢查與自然語言問答沒有](figures/llm-wiki-without-ai.svg)

**沒有 AI 時**（【推論】）：wiki 是 markdown 加 git，仍可讀可改，只是不會自己成長；命中既有簽章、寫入與機械 lint 照常；新案件會堆積，頁面敘述退回附加而變長難讀。

![圖：維運節奏：每個案件、每天、每週或每月、改模型或規則時、規模變大時，各由誰做什麼](figures/llm-wiki-cadence.svg)

**維運節奏**（【建議】，沒有長期運作的實測）：每個案件由程式查簽章、沒命中才請 AI 分析、人核准、程式寫入；每天程式跑 lint、人處理 error；每週或每月人與 AI 一起看 warn 與 info、清理待審區、檢討誤命中與漏命中；改模型、prompt 或規則時用案例集回歸；規模變大時檢討 `index.md` 是否夠用。**AI 用量隨命中率下降**是推論，沒有實際用量數據。

### 5.6 什麼情況適合，以及風險

| 情況 | 判斷 |
|---|---|
| 資料約 100 份、數百頁 | 適合（【原文】用 index 即可，不需要 embedding 式 RAG） |
| 資料量遠大於此 | 要評估，可能要搭配搜尋或 RAG；我沒有資料 |
| 要即時反映來源最新狀態 | 要承擔重新匯入的落差（【二手】） |
| 答案要可追溯、可稽核 | 適合：保留原始資料與 log，頁面引用來源 |
| 沒有人審閱、錯誤會累積 | **不建議**（【推論】） |

主要風險（【建議】與【推論】）：**錯誤會被累積**；**過時**（來源更新後 wiki 不會自動跟上，要靠 lint 與重新匯入，【二手】）；**矛盾與淘汰**（留言串提到尚未解決，我只看到摘要）；**成本**（一次 ingest 動到 10–15 頁，我沒有估算）；**安全**（外部資料交給有寫入權限的 agent，要注意 prompt injection，schema 要寫明資料是不可信輸入並限制只能寫 wiki 目錄）；**權限**（摘要頁是衍生內容）；社群實作良莠不齊（【二手】說已有 30 多個，我沒確認）。

### 5.7 實作要點（示意）

gist 沒有給固定結構，下面是我依它的描述整理的示意（【建議】，沒有實作過）。

```text
my-wiki/
  raw/                  # 原始資料，唯讀（不要讓 LLM 改它）
  wiki/
    index.md            # 每頁一行：連結、一句話摘要
    log.md              # 只增不改：## [2026-11-23] ingest | 標題
    sources/            # 每份原始資料一頁摘要
    concepts/           # 概念與實體頁
  CLAUDE.md             # schema：規定 LLM 怎麼匯入、查詢、健檢
```

schema 該寫什麼（【建議】）：

```markdown
# Wiki 維護規則（示意）

## 匯入（ingest）
- 一次只處理一份 raw/ 內的資料；先摘要給我看，確認後再寫入。
- 每份資料建立 sources/ 的一頁；更新相關的 concepts/ 頁；更新 index.md；在 log.md 加一筆。
- 每個論述都要標註來源（連到 sources/ 的頁面）；不確定的寫「待確認」，不要編造。

## 查詢（query）
- 先讀 index.md 找頁面，再讀頁面；回答要附引用。
- 好的答案要先問我，再存成新頁面。

## 健檢（lint）
- 找：互相矛盾的說法、沒有來源的論述、孤立頁、index 沒收錄的頁、過時的內容。
- 只列出問題與建議的修正，經我同意再改。

## 禁止
- 不得修改 raw/ 內的任何檔案。
```

- **來源要可追溯**：每頁都引用 `sources/`，這樣 lint 與人工審閱才抓得到錯。
- **版本管理**：用 git；每次 ingest 一個 commit，方便回溯與還原（【原文】說 wiki 就是 git repo）。
- **人在迴圈**：匯入時先讓你看摘要與要改的頁面，再寫入；不要全自動（【建議】）。

| **重點** | 找得到、讀得懂、依據是**權威版本** | **累積、版本與狀態、可信度**：以前發生過嗎、修好了沒、這個版本還會發生嗎 |

### 6.1 issue 排查的查詢流程（設計構想）

![圖：issue 排查的查詢流程：工程師提問，閘道層驗證身分，並行查案件資料庫與 wiki、MCP 工具、RAG、程式碼搜尋，彙整答案附引用；已知問題連到根因頁，否則分析、人工核准、寫入 wiki](figures/enterprise-kb-troubleshoot.svg)

- 並行查四路，**彙整時附引用與來源連結**（【本庫】可追溯是企業 RAG 的硬性要求之一）。

## 7. 共同底座：metadata、生命週期、權限與評測

![圖：每份知識的生命週期：草稿經審閱核准成為已核准；定期確認仍有效；超過期限沒確認進入待複查；確認不再有效就淘汰；右邊是共同欄位](figures/enterprise-kb-lifecycle.svg)

**共同欄位**（【建議】）：負責人（owner）、適用範圍與版本、狀態（草稿、已核准、已淘汰）、來源連結、最後確認日期、權限（誰能看）。**沒有負責人與過期機制，任何知識庫都會腐爛。**

**企業環境的硬性要求**（【本庫】對 RAG 的整理，也適用於這個系統）：

| 要求 | 做法 |
|---|---|
| 權限 | 檢索時依使用者身分過濾；ACL 隨 metadata 進索引 |
| 資料新鮮度 | 增量同步；刪除與修訂要能從索引移除，否則答案會引用已撤銷的規定 |
| 可追溯 | 每個答案附引用並保留來源連結 |
| 稽核紀錄 | 記錄誰在何時問了什麼、用了哪些文件 |
| 資料不外流 | 選用符合合規的部署與服務條款；敏感文件分級 |
| 評估與監控 | 固定評估集、線上回饋、定期回歸測試；資料與模型一變，品質就可能退步 |

**人在迴路**：【本庫】經驗型知識（wiki）要**人工核准才寫入**；接內部系統要**先唯讀**，寫入類能力要有開關與稽核，高風險寫入一律人工審核。

## 8. 知識回饋整理：讓知識庫愈用愈準

![圖：知識回饋整理的八個步驟：收集、分類、路由、草稿、人工審核、寫回、驗證、結案；駁回時不寫入並記錄原因，驗證變差時退回修改](figures/enterprise-kb-feedback-flow.svg)

**範圍**：這裡的「知識回饋整理」是指把**使用中產生的回饋、修正與新經驗，整理後寫回知識庫**，讓答案隨使用愈來愈準。本庫目前只有簡短提到：[Enterprise-AI-Integration](Enterprise-AI-Integration.md) 把「回饋管道」列為試點上線的條件、把「線上回饋」列為評估與監控的一部分（【本庫】）；第 5.5 節有 wiki 的人工核准與維運節奏（【本庫】）。**完整的回饋整理流程沒有在本庫設計過，以下是我的設計建議（【建議】），沒有實作或驗證。**

### 8.1 回饋從哪裡來

| 來源 | 例子 | 代表什麼 |
|---|---|---|
| 使用者對答案的回饋 | 有用、沒用、指出哪裡錯、提供修正 | 答案或引用有問題 |
| 查無結果的問題 | 問了但知識庫答不出來 | 知識缺口 |
| issue 結案 | 根因、修復版本、這次沒記錄的做法 | 新經驗要補進來 |
| 引用到過時或錯誤內容 | 使用者或工程師回報 | 該頁面要更新或淘汰 |
| 維護流程的發現 | lint、過期審查、回歸（已修復的版本又出現） | 知識與現況不符 |
| 事故檢討 | 新的教訓與做法 | 要補進 runbook 或案例 |

【實作】coredump 範例已有兩個這類訊號：`regression`（已標記修復的版本又出現）與 lint 抓到的回歸，見 [Claude-Coredump-Wiki](Claude-Coredump-Wiki.md)；其他來源（使用者按鈕、查無結果統計）**沒有實作**。

### 8.2 流程（八個步驟）

1. **收集**：程式收集並去重（同一件事被回報很多次，只算一件、記次數）。
2. **分類**：先判斷是哪一種問題，處理方式不同（見 8.3）。
3. **路由**：依知識型態與範圍，交給該知識的負責人；**沒有負責人的知識，回饋沒人接**（第 7 節）。
4. **草稿**：AI 或程式把零散的回饋整理成修改草稿，附上來源回饋；草稿只放在待審區，不直接改正式內容。
5. **人工審核**：確認回饋屬實、決定怎麼改；**這一步不能省**，與第 5.5 節的核准原則一致。駁回就不寫入，記錄原因後結案。
6. **寫回**：寫入並留痕（8.5）。
7. **驗證**：用評測集回歸，確認這次修改沒有讓其他問題變差；變差就退回修改。
8. **結案**：通知提供回饋的人，並記錄結果；有人收到回覆，回饋管道才有人願意用。

### 8.3 分類：不同問題，不同處理

| 類型 | 典型情況 | 主要處理 | 誰決定 |
|---|---|---|---|
| 答案錯 | 知識庫有正確內容，但檢索或整理出錯 | 檢查檢索與引用；必要時改頁面結構或 metadata | 該知識的負責人 |
| 知識缺 | 查無結果，或回饋指出沒有這份內容 | 新增內容，走一般的草稿與審核 | 負責人 |
| 知識過時 | 引用的內容已不符現況 | 更新，或標記為待複查、淘汰（第 7 節生命週期） | 負責人 |
| 權限問題 | 看到不該看的內容，或該看的看不到 | 修正權限與 metadata；**不要用複製內容的方式繞過** | 權限的負責人與資安 |
| 使用者誤解 | 回饋本身不正確 | 不改內容；必要時補說明，讓內容更不易被誤解 | 負責人 |

這個分類是我的歸納（【建議】），**類別與處理方式沒有經過實際案例驗證**；你們可能需要增減。

### 8.4 人、AI、程式怎麼分工

![圖：知識回饋整理的三方分工：程式收集去重、分類路由、回歸與寫入；AI 整理草稿、找相關頁面、提建議，不直接寫入；人確認屬實、決定怎麼改、核准或駁回；另有三條規則](figures/enterprise-kb-feedback-roles.svg)

- **程式**：收集與去重、依規則分類與路由、跑評測集回歸、寫入頁面與 log、提醒逾期並統計指標。
- **AI**：把零散回饋整理成草稿、找出相關頁面與可能重複、提出修正建議、彙整查無結果的問題；**不直接寫入**。
- **人**：確認回饋屬實、決定怎麼改、核准或駁回、處理權限問題、決定評測集與政策。

**三條規則**（【建議】）：

1. **使用者的修正本身也要查證**：回饋可能是誤解，也可能是被誤導；人確認屬實後才寫入，不能直接當成事實。
2. **回饋與草稿是衍生內容**：可能含有原文權限外的資訊，要依權限控管（與第 5.3 節的摘要頁同一個問題）。
3. **每則回饋要有負責人與期限**：沒有人處理，回饋管道很快就沒人用。

### 8.5 寫回要留痕

每次寫回至少記錄（【建議】，與第 7 節的共同欄位對應）：

- 更新後的**版本**與**狀態**（草稿、已核准、待複查、已淘汰）。
- **最後確認日期**與確認的人。
- **來源回饋**：是哪一則回饋觸發的（可以回頭查）。
- **log 一筆**：做了什麼、誰核准；【實作】coredump 範例的 `approve`、`mark-fixed` 與 `merge-rejected` 都會寫 log 並做 git commit，同樣的留痕方式可以沿用。

### 8.6 風險

| 風險 | 為什麼 | 對策（建議） |
|---|---|---|
| 把未經查證的回饋當成事實 | 使用者可能搞錯，也可能被誤導 | 人工審核；回饋要附證據才進草稿 |
| 回饋洩漏權限外的資訊 | 回饋內容與草稿是衍生內容 | 依權限控管；草稿繼承來源的權限 |
| 回饋堆積沒人處理 | 沒有負責人與期限 | 每則回饋有負責人與期限；逾期提醒 |
| 評測集被污染 | 用回饋補評測集時，若和調整用的資料混在一起，回歸測試會失真 | 評測用的資料與調整用的資料分開 |
| 一則回饋改動太多頁面 | 一次動到很多頁，更難審閱 | 拆成多個草稿，各自審核與驗證 |
| 修改造成別處變差 | 改一頁可能影響其他問題的答案 | 寫回後用評測集回歸，變差就退回 |

### 8.7 可以追蹤的指標

【建議】數字與門檻由你們定，**我沒有任何基準值**：

- **回饋處理時間**：從收到到結案。
- **查無結果率**：問了答不出來的比例，下降代表缺口被補上。
- **重複問題比例**：同一個問題一再被問，代表之前的回饋沒有真正解決。
- **命中已知問題的比例**（issue 排查）：已知問題是否被認出來。
- **回歸測試的變化**：寫回之後，評測集的結果有沒有退步。
- **駁回比例與原因**：太高代表回饋品質或收集方式需要調整。

**不建議**把「回饋數量」當成成效，因為數量多可能只是答案不準。

## 9. 導入順序

![圖：導入順序的五個階段與過關條件：盤點、選一個高價值場景、最小版本、評測、擴充與治理](figures/enterprise-kb-rollout.svg)

1. **盤點**：各知識庫放在哪、誰維護、更新頻率、權限模型、能不能送外部 API。
2. **選一個高價值場景**：我傾向 issue 排查（【推論】重複問題多、命中率與解決時間可以量，且本庫已有 coredump 的設計與範例可參考）；你們的優先順序可能不同。
3. **最小版本**：該場景對應的機制，只接 1–2 個知識庫，不先整合所有庫。
4. **評測**：用真實問題建評測集，量命中率與錯誤率；換模型或資料前回歸（【本庫】）。
5. **擴充與治理**：擴到功能開發；補核准流程、權限、過期審查與資料外送政策。

**沒有工期估計**：我沒有你們的人力與資料量，不編數字；過關條件的門檻由你們決定。

## 10. 需要你先確認的事

這些答案會改變結論：

1. **現有知識庫**在哪些系統（Wiki、文件庫、Git、Jira、其他），各有多少內容、多久更新一次？
2. **權限**怎麼分（依專案、部門、還是個人）？有沒有資料**不能送外部 API**？
3. **使用者**是誰、有多少人？最大的痛點是**找不到、過時、還是重複問**？
4. **既有的搜尋或 AI 工具**是什麼？能不能沿用，還是要整合？
5. **排查經驗**目前記在哪裡？有沒有結構化的案件紀錄（簽章、版本、狀態）？
6. **誰能當負責人與核准者**？沒有人負責，wiki 與生命週期都無法運作。
7. **回饋現在怎麼收**？有沒有按鈕、表單，還是只靠人反映？查無結果的問題有沒有被記錄？
8. **回饋由誰處理、多久內處理**？沒有負責人與期限，第 8 節的流程不會運作。

## 11. 要避免的事

![圖：要避免的五件事與對策（另有第 6 項影子 AI，見下方文字）：全部塞進同一個向量庫、AI 自動寫入沒人審閱、忽略權限、沒有負責人與過期機制、一次做完](figures/enterprise-kb-pitfalls.svg)

1. **把所有內容塞進同一個向量庫**：型態、更新節奏與權限不同，會互相拖累（【建議】）。
2. **讓 AI 自動寫入而沒有人審閱**：錯誤會被累積並被後續引用（【原文】、第 5 節）。
3. **忽略權限**：模型不會自己守權限（【本庫】）；摘要頁是衍生內容，也要控管。
4. **沒有負責人與過期機制**：知識庫會腐爛（【建議】）。
5. **一次做完**：先一個場景，由輕到重（【本庫】）。
6. **影子 AI**（圖外補充）：沒有核准的入口與政策，員工會自己用未受管控的工具（【本庫】治理）。
7. **回饋收了不處理，或未查證就寫進去**（圖外補充）：前者讓管道失效，後者讓錯誤進入知識庫（【建議】，第 8 節）。
