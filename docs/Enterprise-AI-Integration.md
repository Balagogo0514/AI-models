## 一、先給答案

| 問題 | 簡短回答 |
|------|----------|
| 「整合」只是接一個模型 API 嗎？ | 不是。模型只是其中一層，還要接**資料**（RAG）、**系統**（工具／MCP）、**權限與稽核**（閘道層），並持續**評估與營運**。 |
| 怎麼開始最穩？ | 由輕到重：先提示詞與工作流 → RAG → 工具整合 → Agent → 微調 → 自建服務。**上一層解決不了，才往下一層。** |
| 流程怎麼走？ | 八個階段（見 §三），每階段有產出與「過關條件」，沒過就不往下。 |
| 資源怎麼判斷？ | 看五件事：資料敏感度與合規、請求量、延遲、客製化程度、自己能不能維運。先用商用 API 做 POC，數字出來再決定自架或微調。 |

## 二、整合模型的六個層次

![整合模型的六個層次：提示詞與工作流、RAG、工具與 MCP 整合、Agent 編排、微調、自建模型服務；以點數表示人力、資料準備、運算與成本、風險的相對需求](figures/enterprise-integration-matrix.svg)

| 層次 | 解決什麼 | 什麼時候才需要 | 先看哪裡 |
|------|----------|----------------|----------|
| 1 提示詞與工作流 | 輸出格式、固定流程 | 任何專案的起點 | — |
| 2 RAG | 模型不知道內部事實 | 答案要依據內部文件 | 〈[Enterprise-RAG](Enterprise-RAG.md)〉 |
| 3 工具／MCP 整合 | 要**即時**資料或**執行動作** | 答案是「現在的值」或要寫入系統 | 〈[Enterprise-RAG](Enterprise-RAG.md)〉§五、§六 |
| 4 Agent 編排 | 多步驟、需要模型自己決定下一步 | 固定流程寫不完所有分支 | 〈[Agentic-Engineering](Agentic-Engineering.md)〉 |
| 5 微調 | 行為、格式、術語 | RAG 與提示詞都改善不了行為 | 〈[Post-Training](Post-Training.md)〉 |
| 6 自建模型服務 | 資料不能出境、規模化後的成本與延遲 | 合規或成本交叉點逼你自架 | 本文 §六 |

> 圖中的點數是**相對等級**，用來比較層次之間的差異，不是精確數字。🛠

## 三、端到端流程：八個階段與過關條件

![整合流程的八個階段：定義問題與指標、盤點系統與資料、建評估集與基線、POC、整合設計、試點上線、規模化與治理、持續營運，每個階段有主要產出與過關條件](figures/enterprise-integration-stages.svg)

| 階段 | 做什麼 | 產出 | 過關條件 | 常見失敗 |
|------|--------|------|----------|----------|
| 0 定義問題與指標 | 選一個有明確價值的情境；寫下成功指標 | 情境說明、指標、現況基線 | 目標**可量測** | 「先導入再說」，沒有指標，事後說不清有沒有效 |
| 1 盤點系統與資料 | 列出要接的資料與系統，分級，確認能否合法使用 | 系統與資料清單、分級 | 資料**可合法使用且可接入** | 發現資料散落、沒有 API、含個資才回頭補 |
| 2 建評估集與基線 | 蒐集真實問題與標準答案，量測現況 | 評估題集、基線分數 | 題集**有代表性** | 只用幾題示範，無法回歸比較 |
| 3 POC（商用 API） | 用商用 API 加 RAG 與工具做最小原型 | 原型、評估分數、成本估算 | 達評估門檻、**成本可估** | 一開始就自架或微調，花了力氣卻不知道瓶頸在哪 |
| 4 整合設計 | 設計權限、資料流、介面、閘道層 | 架構與資料流圖、審查結論 | 通過資安與合規審查 | 權限最後才補，只好重做索引與介面 |
| 5 試點上線 | 小範圍使用者、人工複核 | 錯誤樣本、回饋 | 錯誤率與回饋達標 | 沒有回饋管道，問題只靠使用者抱怨才發現 |
| 6 規模化與治理 | 擴大範圍，上配額、成本監控、治理流程 | 營運手冊、成本報表 | 成本與風險**可控** | 用量暴增才發現沒有限流與預算 |
| 7 持續營運 | 監控、回歸、模型與資料更替 | 儀表板、回歸報告 | 回歸測試通過才換版 | 換模型沒跑評估，品質悄悄退步 |

**模型或資料換版時**：回到階段 2、3 重跑評估，通過才切換。官方定價頁也標出已**退役**的舊模型（例如 Opus 4.1、Opus 4、Sonnet 4，只剩部分雲端平台仍提供）✅，所以版本更替是必然會發生的事，要把「固定版本、追蹤棄用公告、換版前跑回歸」寫進營運流程。

## 四、參考架構

![參考架構：使用者與內部應用經 AI 閘道層（身分、金鑰、配額、日誌、遮罩、模型路由、快取）進入編排層與模型，編排層經工具介面存取內部系統；可觀測性橫跨所有層](figures/enterprise-integration-architecture.svg)

### 4.1 為什麼要有「閘道層」

不要讓每個應用各自拿金鑰直連模型。🛠 在中間放一層統一入口，可以集中處理：

| 能力 | 價值 |
|------|------|
| 身分驗證與權限 | 知道是誰在問，才能依身分過濾資料 |
| 金鑰管理 | 金鑰不散落在各應用；輪替與撤銷集中處理 |
| 配額與限流 | 防止用量與成本失控 |
| 日誌與稽核 | 記錄誰、何時、問了什麼、用了哪些資料 |
| 敏感資料遮罩 | 送出前先遮罩個資與機密 |
| 模型路由與備援 | 依任務選模型；某個服務失敗時切換 |
| 快取 | 相同或相似請求不重複付費 |

### 4.2 工程整合清單

- **抽象層**：應用呼叫的是「你的介面」，而不是某家的 SDK 細節，降低換模型的成本。
- **逾時、重試、退避**：模型服務可能偶發失敗或變慢。
- **版本固定**：指定明確的模型版本，不用「最新」別名，避免行為悄悄改變。
- **可觀測性**：追蹤每次呼叫的延遲、token 用量、成本、評估分數，並能回溯到原始請求。
- **隔離環境**：開發、測試、正式環境分開，金鑰與資料也分開。

## 五、接內部系統：權限階梯

![接內部系統的權限階梯：L1 唯讀查詢、L2 產生草稿或建議、L3 低風險寫入、L4 高風險寫入，每往上一級都要前一級已穩定、評估通過、稽核可查、可關閉](figures/enterprise-integration-ladder.svg)

### 5.1 原則

1. **先唯讀**：從 L1 開始。穩定、評估通過之後才開放下一級。
2. **身分怎麼帶**：優先讓 AI 以**使用者的身分**存取資料（使用者看不到的，AI 也看不到）；只有必要時才用權限受限的**服務帳號**，並限制它能做的事。🛠
3. **可關閉**：每個寫入類能力都要有開關（kill switch），出問題能立刻停。
4. **人在迴路**：L4 一律人工審核後才執行；L3 也要有完整紀錄與回復方式。

### 5.2 各種內部系統怎麼接 🛠

| 系統 | 建議接法 | 注意 |
|------|----------|------|
| 資料庫 | 唯讀帳號或檢視表（view），只暴露需要的欄位 | 官方 MCP 文件的範例也建議使用唯讀資料庫帳號 ✅；避免讓模型任意拼 SQL 打正式庫 |
| 內部 REST API | 包成工具（function calling 或 MCP） | 工具描述要精準；輸入輸出要驗證；回傳量要限制 |
| ERP／CRM | 先唯讀查詢，再開「建立草稿」 | 寫入前要有人確認；注意稽核欄位 |
| 工單系統 | 查詢、建立草稿、加註解，逐級放寬 | 避免自動關單、批次變更 |
| 程式碼庫 | 用在沙箱中的 coding agent，成果走 PR 與審查 | 權限、密鑰與執行環境隔離；見〈[Claude-Code-CLI](Claude-Code-CLI.md)〉 |
| 文件與知識庫 | RAG 索引，權限寫進 metadata | 見〈[Enterprise-RAG](Enterprise-RAG.md)〉 |

MCP 的安全警告、scope 與組織管控（`managedMcpServers`、`allowedMcpServers`／`deniedMcpServers` 等）、tool search 與輸出上限，詳見〈[Enterprise-RAG](Enterprise-RAG.md)〉§六。✅

## 六、資源判斷

### 6.1 人力與角色 🛠

| 角色 | 主要負責 | 什麼階段最需要 |
|------|----------|----------------|
| 領域專家／業務 | 定義問題、決定什麼算「答對」、審查評估題集 | 0、2、5 |
| 產品／專案 | 目標、關卡、範圍與時程 | 0、6 |
| 資料工程 | 盤點、清洗、同步、索引、metadata 與權限 | 1、3、4 |
| 應用／後端工程 | 編排、工具介面、閘道層整合 | 3、4、6 |
| ML／評估工程 | 評估集與指標、（需要時）微調與模型服務 | 2、3、7；層次 5、6 |
| 平台／SRE | 部署、監控、容量、成本 | 4、6、7 |
| 資安與合規 | 資料分級、權限、稽核、供應商審查 | 1、4、6 |

POC 階段一個小團隊兼任多個角色即可；規模化後再拆分。**自架模型或微調**會明顯增加 ML 與平台的需求，這是決定要不要往下一層時最容易低估的成本。

### 6.2 資料資源

| 層次 | 需要準備什麼 |
|------|--------------|
| 提示詞與工作流 | 範例輸入輸出即可 |
| RAG | 清洗過的文件、版本與權限 metadata、更新機制 |
| 工具／MCP | 可呼叫的 API、測試資料與沙箱環境 |
| 微調 | 高品質的「輸入→理想輸出」資料，且要有人標註與審查；量與品質的要求見〈[Post-Training](Post-Training.md)〉 |
| 自建服務 | 同上，加上部署與壓測用的流量樣本 |

### 6.3 API、自架、還是微調？

![判斷流程：先問資料能否送出企業邊界；不能走自架；能就用商用 API 加 RAG 與工具做 POC；達標維持 API；沒達標則依瓶頸修資料與檢索、微調或評估較小模型與自架](figures/enterprise-integration-decision.svg)

| 判斷面向 | 傾向商用 API | 傾向自架 |
|----------|--------------|----------|
| 資料敏感度與合規 | 合約與條款能滿足 | 資料不能出企業邊界 |
| 請求量 | 量小或波動大（用多少付多少） | 量大且穩定（硬體稼動率高） |
| 延遲 | 一般延遲可接受 | 需要極低延遲或離線運作 |
| 客製化 | 提示詞與 RAG 足夠 | 需要深度客製或自有模型 |
| 維運能力 | 不想養模型服務團隊 | 有 ML 與平台團隊 |
| 成本 | 月費隨用量線性增加 | 固定成本高，量大後單位成本才攤得下來 |

> 是否一定要開源或自架，取決於合規與成本，不是「做 RAG 就一定要」。詳見〈[Post-Training](Post-Training.md)〉的「只做 RAG，還需要開源模型嗎？」。

### 6.4 用 API 的成本怎麼估

**公式**：

```text
月成本 = 月請求數 × (平均輸入 tokens × 輸入單價 + 平均輸出 tokens × 輸出單價) ÷ 1,000,000
```

**官方單價（摘選，每百萬 tokens，美元）✅**，來源：Anthropic 定價頁，2026-11-07 讀取，實際以當期定價頁為準：

| 模型 | 輸入 | 輸出 | 快取讀取 |
|------|------|------|----------|
| Claude Fable 5.1 | $10 | $50 | $0.25（0.025 倍） |
| Claude Opus 5.5 | $4 | $20 | $0.20（0.05 倍） |
| Claude Sonnet 5.5 | $2 | $10 | $0.10（0.05 倍） |
| Claude Haiku 5.5（prompt ≤100K tokens） | $0.10 | $0.50 | $0.01 |
| Claude Haiku 5.5（prompt >100K tokens） | $0.50 | $2.50 | $0.05 |

**官方載明的降成本機制** ✅：

- **提示詞快取**：5 分鐘快取寫入為輸入價的 1.25 倍、1 小時為 2 倍；讀取（命中）一般為 0.1 倍，Opus 5.5 與 Sonnet 5.5 為 0.05 倍，Fable 5.1 為 0.025 倍。
- **Batch API**：輸入與輸出都 **5 折**，但是非同步處理。
- Claude 4.6 以後的模型（Haiku 5.5 除外）以標準價包含完整 **1M token** context；Haiku 5.5 依單次 prompt 長度分兩段計價（計入快取讀寫的 tokens）。
- 資料駐留：指定 `inference_geo: "us"` 時為 1.1 倍價格。

![以 Sonnet 5.5 為例的月成本：基線約 1,700 美元；固定前綴命中快取約 940 美元；全部批次約 850 美元；全部改用 Haiku 5.5 約 85 美元但品質需另評](figures/enterprise-integration-cost.svg)

**範例 ⚠️（假設值，請換成你的數字）**：每月 10 萬次請求，每次輸入 6,000 tokens（RAG 片段加 prompt）、輸出 500 tokens，用 Sonnet 5.5：

| 情境 | 算法 | 月成本 |
|------|------|--------|
| 基線 | 輸入 600 MTok × $2 + 輸出 50 MTok × $10 | **$1,700** |
| 固定前綴 4,000 tokens 命中快取 | 輸入 400 MTok × $0.10 + 200 MTok × $2 ＋ 輸出 $500 | **$940**（未計快取寫入） |
| 全部走 Batch | 基線 × 0.5 | **$850** |
| 全部改用 Haiku 5.5 | 輸入 600 MTok × $0.10 + 輸出 50 MTok × $0.50 | **$85**（品質需另評） |

- 快取的實際效益取決於**命中率與 TTL**；沒命中的部分要付寫入價。
- 批次不適合需要即時回應的互動式問答。
- 改用小模型之前，要用評估集確認品質；價格低不等於划算。

### 6.5 自架的 GPU 記憶體怎麼估

![自架記憶體估算：權重約等於參數量乘以每參數位元組數，70B 在 FP16 約 140 GB、INT8 約 70 GB、4 位元約 35 GB，7B 在 FP16 約 14 GB；KV cache 以類似 70B 的 GQA 配置示意，8K 長度 16 並發約 40 GiB](figures/enterprise-integration-sizing.svg)

- **權重** ≈ 參數量 × 每個參數的位元組數（FP16／BF16 為 2、INT8 為 1、4 位元約 0.5）。🛠
- **KV cache** ≈ 2 × 層數 × KV heads × head_dim × 位元組 × token 數 × 並發數。KV cache 的成因與 MQA／GQA／MLA 如何縮小它，見〈[Transformer-Attention](Transformer-Attention.md)〉。
- 圖中的 KV cache 是以「類似 70B 的 GQA 配置」（80 層、8 個 KV heads、head_dim 128、FP16）示意 ⚠️，實際請查**該模型的 config**。
- 總需求還要加上執行時開銷，並依單卡記憶體與切分方式（張量並行等）換算成卡數。
- 自架的成本不只 GPU：還有維運人力、監控、備援、模型更新與資安。**稼動率低時，自架通常比 API 貴。**🛠

### 6.6 微調需要的資源

不給固定數字，只列要評估的項目（細節見〈[Post-Training](Post-Training.md)〉）：

- **資料**：高品質、有人審查的訓練資料；資料量與品質往往比算力更是瓶頸。
- **評估**：要有能分辨「微調前後是否更好」的評估集，否則無法驗證。
- **算力**：視方法而定（全量微調、LoRA 等參數高效方法所需資源差異很大）。
- **維運**：微調後的模型要自己部署、版本管理與回歸測試；基礎模型換版時可能要重做。
- **前提**：先確認問題真的是**行為、格式或術語**，而不是檢索或資料品質問題。

## 七、治理與風險 🛠

| 風險 | 做法 |
|------|------|
| 資料外洩 | 資料分級；敏感資料遮罩；選符合合規的服務條款與部署方式 |
| 權限繞過 | 依使用者身分過濾；不用一個高權限帳號代替所有人 |
| Prompt injection | 檢索內容與工具結果都視為不可信輸入；不讓它們直接觸發高風險動作；官方 MCP 文件也警告會抓取外部內容的 server 有此風險 ✅ |
| 誤操作 | 權限階梯；寫入類加審核；可回復；kill switch |
| 品質退步 | 固定評估集；換模型或資料前回歸；上線後持續抽樣檢查 |
| 成本失控 | 閘道層配額與預算告警；快取、批次、模型分級 |
| 供應商與版本 | 抽象層；固定版本；追蹤棄用公告；保留備援方案 |
| 影子 AI | 提供核准的入口與政策，否則員工會自己用未受管控的工具 |

## 八、Go／No-Go 檢查清單

**進入 POC 之前**

- [ ] 有一個有明確價值、可量測的情境
- [ ] 資料已盤點、分級，能合法使用
- [ ] 評估題集已建立，基線已量測

**進入試點之前**

- [ ] POC 在評估集上達到門檻，成本可估
- [ ] 權限、資料流與閘道層設計通過資安與合規審查
- [ ] 只開放 L1（唯讀）；寫入類功能有關閉開關
- [ ] 有人工複核與回饋管道

**進入規模化之前**

- [ ] 試點的錯誤率與回饋達標
- [ ] 有配額、預算告警與成本報表
- [ ] 有監控與回歸流程；模型版本已固定
- [ ] 有事故處理與回復流程

## 九、常見迷思

| 迷思 | 實情 |
|------|------|
| 整合 AI 就是接一個 API | 還要資料、權限、稽核、評估與營運 |
| 一開始就該自架或微調 | 先用商用 API 做 POC，才知道瓶頸在哪，也才算得出成本交叉點 |
| 價格最低的模型最划算 | 要用評估集確認品質；錯誤的成本常比 token 費用高 |
| 自架一定比較便宜 | 稼動率低、維運人力多時，通常比 API 貴 |
| 上線後就不用管 | 模型、資料、需求都會變；沒有回歸測試，品質會悄悄退步 |
| 權限交給模型自己守 | 權限要在資料與工具層落實 |
