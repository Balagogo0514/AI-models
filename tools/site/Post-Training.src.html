AI Post-Training

AI 的「後訓練」（post-training）是指模型完成預訓練（pretraining）後，為了讓模型更符合任務需求、回答偏好、安全規範與推理能力，而追加的一系列訓練與優化方法。

預訓練解決「模型看過很多資料」
後訓練解決「模型更會做事、更像你要的助手」

後訓練在做什麼

  • 指令遵循：更會照需求完成任務
  • 領域適配：更懂醫療、法律、金融、企業內部知識
  • 回答偏好：更符合人類期待的品質、格式與風格
  • 安全對齊：降低有害、越獄、違規輸出
  • 推理與工具使用：更會做多步推理、調用工具、產出結構化結果

常見方法

1

SFT / 監督式微調

SFT（Supervised Fine-Tuning）是最常見的後訓練方法。用高品質的指令資料、問答資料、範例輸出，直接監督模型學習。

適合場景

  • 指令跟隨
  • 摘要、翻譯、分類
  • 客服機器人
  • 程式助手
  • 特定語氣或格式輸出

優點

  • 直接、穩定、成本相對可控
  • 是大多數後訓練流程的基礎步驟

限制

  • 模型會模仿資料品質
  • 不一定能學到「哪個答案更好」
2

Continued Pretraining / Domain Adaptation

在預訓練後，用特定領域的大量語料繼續訓練模型。有些人把它和狹義 post-training 分開談，但實務上常一起討論。

適合場景

  • 醫療、法律、金融模型
  • 公司內部知識或專屬術語
  • 特定語言或產業資料強化

優點

  • 能補足模型對領域語料的理解
  • 後續再做 SFT 效果通常更穩

限制

  • 需要大量乾淨領域資料
  • 成本通常高於一般 LoRA 型微調
3

Preference Learning / 偏好學習

重點不是只學「正確答案」，而是學「比較好的答案」。常見做法是蒐集 A/B 回答排序，讓模型理解人類偏好。

  • RLHF：Reinforcement Learning from Human Feedback
  • RLAIF：Reinforcement Learning from AI Feedback
  • DPO：Direct Preference Optimization
  • IPO、ORPO、SimPO：偏好優化的不同變體

適合場景

  • 幫助模型更自然、更有幫助
  • 優化回覆品質、風格、一致性
  • 提升拒答與安全對齊表現

優點

  • 能更直接優化「回答品質」
  • DPO 類方法通常比完整 RLHF 更容易訓練

限制

  • 偏好資料品質決定上限
  • 偏好本身可能主觀且有分佈偏差
4

RL 後訓練

強化學習後訓練會根據 reward 來優化模型策略，特別適合有可驗證目標的任務。

  • RLHF：用人類偏好資料訓練 reward model，再用 RL 優化模型
  • RLAIF：用 AI 提供偏好訊號或評分，降低人工標註成本
  • Verifier-based / Rule-based RL：用規則或驗證器直接給 reward，例如數學答案、單元測試、編譯結果
  • Environment / Tool-interaction RL：讓模型和工具或環境互動，再依任務完成度給 reward
  • Self-play / Self-improvement RL：模型自己生成題目、答案、對局或候選解，再透過對抗、比較或篩選學習

常見演算法：PPO、REINFORCE、Actor-Critic、GRPO、TRPO，以及其他基於 reward model 或 verifier 的 policy optimization 變體。

適合場景

  • 數學題
  • 程式生成與修復
  • 長鏈推理
  • 有明確評分器或驗證器的任務

優點

  • 能直接針對最終任務結果優化
  • 對推理與 search 型問題常有效

限制

  • 訓練不穩定，調參成本高
  • reward 設計不當會導致 reward hacking

DPO、IPO、ORPO、SimPO 常和 RLHF 放在同一類討論，但嚴格說它們比較屬於偏好優化，不是傳統 RL。在 LLM 場景中，最有價值的通常不是通用 control 型 RL，而是能結合 verifier、工具使用與任務完成率的 RL。

5

Rejection Sampling / Best-of-N

先讓模型生成多個候選答案，再透過規則、reward model、驗證器或人工方式選出較好的結果。用途有兩種：直接當推論策略（生成多次，挑最好的）；或當資料蒐集方式（把篩選後的好答案回灌成 SFT 或偏好資料）。

優點

  • 實作簡單
  • 常能有效提升結果品質

限制

  • 推論成本高
  • 需要好的打分或篩選機制
6

Distillation / 蒸餾

讓大模型當老師、小模型當學生，把能力壓縮到更小、更快、更便宜的模型上。

適合場景

  • 邊緣部署
  • 降低推論成本
  • 需要高吞吐量的產品

優點

  • 兼顧效果與效率
  • 能保留部分大模型能力

限制

  • 小模型仍有容量上限
  • 蒸餾資料與 teacher 輸出品質很重要
7

PEFT / 參數高效微調

PEFT（Parameter-Efficient Fine-Tuning）不是訓練目標，而是訓練方式：只更新少量參數，而不是整個模型。常見方法有 LoRA、QLoRA、Adapter、Prefix Tuning。

適合場景

  • 資源有限
  • 需要快速做多個任務版本
  • 想保留 base model，不做全量改動

優點

  • 成本低
  • 訓練快
  • 部署靈活

限制

  • 能力上限通常不如全參數訓練
  • 對極複雜能力提升未必足夠
8

Safety / Alignment Tuning

專門針對模型安全、合規與拒答策略做調整。

  • 避免違規內容
  • 抵抗 prompt injection 或 jailbreak
  • 改善拒答邏輯
  • 符合產品政策與法規要求

這通常不是單一方法，而是混合 SFT、偏好學習、規則資料與對抗式資料。

9

Tool Use / Agent 能力微調

讓模型更會呼叫函式或 API、搜尋外部知識、使用工具鏈、輸出 JSON / schema，以及做多步規劃與任務分解。

對 agent 系統來說，這類後訓練很重要，因為它決定模型是否真的能穩定操作工具，而不只是生成文字。

RL 的分類與為何有效

類型reward 來源典型用途備註
RLHF人類偏好訓練出的 reward model對話品質、風格、有用性演算法常用 PPO；成本高、不穩定
RLAIF／ConstitutionalAI 依規則或原則評分安全、無害性、降低標註成本reward 品質取決於評分模型
RLVR（可驗證獎勵）規則或程式直接判對錯數學、程式（單元測試）、格式、邏輯題近年最主流；訊號乾淨、可大量擴增
Rubric／LLM-as-judge RL評分標準加模型當裁判寫作、分析等無標準答案的任務想把 RLVR 推到「不可驗證」領域
Agentic／環境 RL任務是否完成（跑程式、操作工具、瀏覽器）工具使用、多步任務、軟體工程多輪、長序列，工程複雜度高
Process 型 RL對推理每一步評分（PRM）長鏈推理標註成本高，實務上不如結果型普及
Self-play／自我改進自己出題、互相對抗或篩選推理、遊戲仍偏研究

演算法層面常見 PPO、REINFORCE 系（含 RLOO），以及 GRPO 與其改良版（如 DAPO）。GRPO 不需要另外訓練 value model，成本比 PPO 低。DPO、IPO、ORPO、SimPO 嚴格說屬偏好優化，不是傳統 RL。

為什麼進版常靠 RL 就有明顯改善

  1. SFT 只能模仿，RL 直接優化結果。SFT 學的是示範答案的樣子，上限被資料品質卡住；RL 讓模型自己生成、以結果當回饋，去學「哪種推理路徑真的會對」。
  2. 可驗證的 reward 便宜又準。數學和程式不需要人標，只要題目加檢查器，就能產生大量、低雜訊的訊號。
  3. 長推理鏈是 RL 帶出來的。模型學到先想再答、回頭檢查、換方法重試；多花推論算力換準確度，這種行為很難靠示範資料教出來。
  4. 基礎模型本來就有潛力。預訓練已讓模型「有時候能做對」，RL 主要是把「偶爾對」變成「穩定對」，所以進版常看到 pass@1 大幅上升。
  5. 成本與迭代速度。相對預訓練，RL 較便宜且可頻繁重跑，所以各家把越來越多算力放在這一段。

需要保留的看法

  • 「只做 RL」是簡化說法。實際上通常還有 SFT 冷啟動、mid-training、蒸餾與大量資料篩選；各家細節多半沒公開，個別模型進版動了什麼無法確認。
  • 改善集中在可驗證的領域：數學、程式、推理、agent 任務。知識量與事實正確性主要仍取決於預訓練。
  • 學界仍有爭論：有研究指出，取樣很多次時，基礎模型的覆蓋率不輸 RL 後的模型，意思是 RL 比較像「銳化」而不是「擴大能力邊界」。這不是定論，也依任務而異。
  • 風險：reward hacking、訓練不穩定、在不可驗證的領域改善不穩定。

以上為截至 2026 年中的整理。

怎麼選

  • 讓模型先變得可用→先做 SFT
  • 讓模型更懂特定領域→continued pretraining 或 domain adaptation
  • 讓回答品質更像人喜歡的樣子→DPO / RLHF / RLAIF
  • 讓模型在數學、程式、推理上更強→加 RL 或 verifier-based training
  • 讓部署更省成本→做蒸餾
  • 算力有限但想快速微調→用 LoRA / QLoRA

企業知識整合：RAG 夠不夠？

用開源模型整合企業自己的知識，通常先做 RAG（檢索增強）。夠不夠，不要憑感覺，拿評測集做錯誤分析，看答錯的題目屬於哪一類。

經驗上，第一類（檢索失敗）通常占最大宗，所以多數團隊先把檢索與資料品質做好，再看是否需要微調。微調不適合用來灌事實：容易幻覺、知識會過期、也難以更新。這是通用判斷，實際比例要看你們自己的評測結果。

RAG 不夠時可以做的 RL

RL 通常不是第一步。先修檢索與資料品質，再用 SFT 處理格式與術語，回答偏好還不夠時用 DPO 這類離線偏好優化，有可驗證的 reward 時才上 RL。

可以做的 RL（依實用性排序）

類型reward 怎麼設計解決什麼難度
RAG 行為 RL答案正確、引用的片段真的包含該論點、沒證據時正確拒答、不亂編有證據卻答錯、幻覺、該拒答卻亂答中

最值得先試的是 RAG 行為 RL：訓練時餵入真實檢索結果（含夾雜的無關文件），reward 同時看「答對、引用正確、沒證據就說不知道」。三項要互相平衡，否則模型會學到「永遠拒答」或「每句都亂貼引用」。搜尋型 Agent RL 適合跨文件、多跳的失敗，但工程最複雜。

動手前的前提

  • 先有 SFT 冷啟動：基礎模型直接上 RL 常不穩。
  • 訓練題與評測題要分開，否則測到的只是背題。
  • 訓練環境要接近正式環境：用同一套檢索、切塊、reranker；換了檢索器，學到的行為可能失效。
  • reward 要防呆：觀察模型有沒有鑽漏洞。
  • 資源：RL 比 SFT 貴很多，可用 LoRA 降低成本；常見框架有 TRL、verl、OpenRLHF，GRPO 是常見起點。

不該用 RL 的情況

  • 失敗主要是檢索或資料品質：先修這個。
  • 沒有可驗證的 reward，也沒有可靠的評分標準。
  • 只是想灌入新知識：這是 RAG 的工作，RL 不負責。
  • 評測集太小、不穩定，無法判斷 RL 有沒有真的變好。

需要保留的看法

  • 這是通用判斷，沒有針對特定企業的資料與失敗案例，實際效益無法預測。
  • RL 教的是行為，不是事實，所以知識更新時不必重訓；但檢索器或切塊方式改了，行為可能要重新校準。
  • 這個領域變動很快，具體方法的效果只整理到 2026 年中。

只做 RAG，還需要開源模型嗎？

RAG 一定需要一個生成答案的語言模型，但不一定要開源。商用 API 搭配 RAG 完全可行，也是很多企業的起點。

RAG 裡的三個模型角色

角色做什麼開源商用 API
Embedding 模型把文件與問題轉成向量，決定檢索品質可以（常見選擇）可以
Reranker對檢索結果重新排序可以可以
生成模型（LLM）讀檢索結果、產生答案可以可以

三個角色可以混搭，例如 embedding 與 reranker 用開源自架，生成用商用 API。

傾向用開源（開放權重）模型的條件

  • 資料不能出公司（法規、客戶合約、機密）：商用 API 要把內容送到外部；即使有「不用於訓練」的條款，部分企業仍不接受。
  • 必須地端或離線運行（內網、隔離環境）：商用 API 需要連網。
  • 要自己控制版本：商用模型可能被下架或改版、行為會變；自架模型版本固定。
  • 要微調（格式、術語、工具使用）：開放權重模型才能自由微調。
  • 呼叫量極大、成本敏感：到一定規模後自架可能較便宜，但要算上 GPU 與維運成本。

傾向用商用 API 的條件

  • 要最強的推理與理解能力，而且資料可以送出去。
  • 團隊沒有 GPU 與 MLOps 能力：自架要處理部署、擴縮、監控與更新。
  • 用量小或還在 PoC：先用 API 驗證價值最快，不必先買硬體。
  • 需要快速上線。

兩個常見迷思

  • 開源不等於免費：自架要付 GPU、電力與人力，小規模時 API 常常更便宜。
  • 開源不等於開放原始碼：多數是「開放權重」，授權條款各異，商用限制要逐一確認。

動手的順序

  • 先釐清限制：資料能不能出去、要不要地端、預算與人力，這幾個答案幾乎直接決定方向。
  • 模型做成可替換：程式用統一介面呼叫，換模型只改設定。
  • 用評測集決定：同一組標準問答，比較開源與商用在自己資料上的表現。
  • 必要時混合：敏感文件走自架模型，一般文件走 API，依資料等級路由。

以上是通用判斷，實際選擇取決於各自的資料敏感度、法規與預算。

一般使用者可做的優化

如果你無法調整大模型權重，能做的通常不是嚴格意義上的 post-training，而是使用層與系統層優化。不過在實務上，這些方法往往比小規模微調更容易落地，也更快見效。

1. Prompt 優化

把任務描述得更清楚，通常是成本最低、效果最直接的做法。

  • 明確寫出目標、限制條件、成功標準
  • 指定輸出格式，例如表格、JSON、固定欄位
  • 提供 1 到 3 個高品質範例
  • 把大任務拆成幾個步驟，降低模型跑偏機率

2. Context 優化

模型常常不是不會，而是缺資訊。把對的資訊放進 context，通常比單純改 prompt 更重要。

  • 補上需求文件、規格、會議紀錄、程式碼片段
  • 用 RAG 或文件檢索把相關資料先找出來再餵給模型
  • 過濾不相關內容，避免 context 被雜訊塞滿
  • 把背景資訊結構化，例如摘要、欄位化、段落標記

3. Workflow 優化

不要把模型當成一次性問答工具，而是把它放進一個可重複的流程。

  • 先產生草稿，再做第二輪改寫或校對
  • 把任務拆成「理解需求 → 產出候選 → 自我檢查 → 最終整理」
  • 多次生成，再做人選或規則篩選
  • 固定常用 prompt template，降低每次輸入波動

4. Tool Use 優化

很多問題不是模型本身能力不足，而是缺少外部工具。

  • 接搜尋，補最新資訊
  • 接計算器或程式執行，降低數學與程式錯誤
  • 接資料庫或 API，讓回答依據真實資料
  • 接格式驗證器或 schema 檢查器，提升輸出穩定性

5. Evaluation 優化

如果沒有評測，你通常無法知道 prompt 變更到底是變好還是變差。

  • 建立一小組固定測題
  • 比較不同 prompt、不同模型、不同參數設定
  • 追蹤正確率、穩定性、格式錯誤率、人工修改量
  • 對高價值任務做人類審核

6. 參數與模型選型

即使不能訓練模型，選對模型與參數也能大幅影響效果。

  • 推理任務選 reasoning 較強的模型
  • 長文件任務選 context window 較大的模型
  • 創意寫作可提高 temperature
  • 穩定格式輸出可降低 temperature，並限制輸出長度

一句話理解　不能改模型權重時，最有效的優化通常不是「訓練模型」，而是讓對的資訊，用對的流程，在對的格式下進模型。

一句話總結　後訓練不是單一技術，而是一整套把「會預測下一個 token 的模型」，變成「能完成任務、符合偏好、可安全部署的模型」的方法組合。
